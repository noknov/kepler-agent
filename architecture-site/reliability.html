持久化与恢复

进程可能在任意一步退出。恢复需要根据已经保存的记录，决定哪些结果可以复用、哪些工作尚未开始、哪些外部操作仍然未知。锁、事件和队列各自只解决其中一部分问题。

权威记录与派生状态

恢复最先需要的是可信的执行记录。会话事件保存用户输入、模型消息、工具开始和结果、等待状态及终态。运行列表、步骤和指标是从这些事件生成的查询视图，称为投影。

把两者分开，是为了避免界面写入失败改变实际执行状态。例如，工具结果已经提交，但运行详情页没有更新，不能据此再执行一次工具。应从事件恢复查询视图。

当前模型上下文也不是完整历史。它是为一次模型调用选择的消息，可能包含摘要或预览；原始事件仍负责说明当时实际保存了什么。

处理权

两个工作进程都能读取同一会话，但不能同时根据同一旧历史推进任务。会话处理权用于限制当前能够推进的人。它和入口任务认领不是同一把锁：入口认领保护待处理工作，会话锁保护连续历史。

托管实现使用专用 PostgreSQL 连接持有会话 advisory lock，并检查该连接是否仍可用。失去确认时取消执行。本地实现使用覆盖整个 turn 的文件锁，多个本机进程也要遵守同一边界。

说明示例

租约到期后的旧处理者

假设工作进程 A 认领了入口事件，但与数据库失联。租约到期后，B 可以按规则接管。A 如果恢复连接，不能不加检查地把任务标成完成，否则可能覆盖 B 的处理状态。

因此，认领续租、完成和释放都需要匹配当前所有者；旧执行者还要停止继续推进。单纯等一个超时时间不构成完整的互斥保证。

托管事件存储

数据库事件需要确定顺序。相同会话的追加在事务中协调，分配递增的会话序号，再提交事件。事件标识用于判断重复追加，序号用于决定历史先后；它们承担不同职责。

如果一次提交的结果对调用方不明确，稳定事件标识可以避免重试写成两条相同事实。但它只能约束事件存储。外部 API 调用不在这个数据库事务中，不能因为事件去重存在，就认为外部操作也只执行一次。

执行器在事件追加成功后才通知投影接收器。这样投影失败可以重建，不会把“界面收到更新”当成权威事件提交的前提。

本地事件存储

本地 JSONL 按行保存事件。多个进程共用同一会话文件时，单纯调用 append 不够：两个执行者可能都读到旧历史，然后分别运行工具。

因此，本地存储区分执行锁和事件锁。执行锁覆盖完整 turn，事件锁只保护一次短暂读写。如果把两种锁混成一把，执行者可能在持有执行锁时，无法再取得写入自己结果所需的锁。

文件索引用事件标识和字节位置加速读取。文件被替换、截断或外部追加后，索引需要更新。修复不完整文件尾部只解决记录格式，不会确认一个中断的外部操作到底有没有完成。

故障窗口

恢复动作取决于退出发生在哪个边界。最重要的区别，是操作意图、执行开始和执行结果不能互相替代。

模型已提出调用，但工具未开始

模型消息中可能已经有工具调用，但还没有工具开始事件。恢复将其记为未开始执行，而不是猜测它已完成。系统需要为这个调用形成明确结果，使后续模型能理解发生了什么。

工具已开始，但没有结果

这时外部操作可能已经成功，只是进程来不及保存结果。例如，下游已经接收了一次写入，响应却在网络中丢失。恢复保留中断或未知状态，不能自动发送同一写入。

结果已保存，但用户没看到

这时应恢复投影或消息投递。重跑模型和工具会把展示故障变成重复执行问题。

同样，“执行开始存在但用户输入缺失”需要补齐输入，“终态已保存”需要恢复已有结果。恢复不是简单地从最后一行代码重新运行。

投影恢复

运行查询需要易于展示的数据结构，例如一行运行摘要和若干步骤。它们可以从事件生成，但生成过程也可能失败或重复收到通知。消费者应利用事件身份保持幂等，并允许从记录重建。

实时文本片段不适合承担同样职责。一个片段只是回答的一部分，可能被界面收到，也可能未收到。持久重放依赖完整消息与生命周期事件，而不是再次发送所有 token 片段。

恢复对账

接管者首先取得会话处理权，然后加载当前执行的记录和累计预算。已经保存的结果可以复用；未完成模型请求与工具调用则按它们留下的证据处理。只有把这些情况区分开，才能决定是否继续。

  1. 确认当前用户、工作区和会话作用域。
  2. 检查是否已有终态；有终态就恢复结果。
  3. 确保原始输入存在，并恢复执行限制与已用预算。
  4. 区分工具尚未开始、结果已保存和结果未知。
  5. 按当前允许的状态继续模型与工具循环，或记录明确结束原因。

即使所有步骤正确，系统仍不具有通用的跨系统 exactly-once 保证。稳定 execution ID 只有被下游实际作为幂等键接受时，才能约束重复写入。不支持查询或幂等的下游，需要保留未知并采用明确的补偿或人工核对。
