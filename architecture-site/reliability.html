STATE / DURABILITY & RECOVERY

记录、并发与恢复

Agent 的可靠性不来自一个更大的锁或一个全局 retry，而来自“事实先落盘、所有权可验证、未知状态不猜测、派生视图可重建”。本页解释 transcript、队列、session lease 和 delivery 之间的边界，以及进程在每个边界退出时下一位 worker 应该怎么判断。

Canonical append-only transcript所有权 owner + lease投影 可重建外部副作用 仍可能未知

权威记录和派生数据必须分开

会话事件是执行恢复的 source of truth。运行列表、步骤、费用、健康汇总和界面状态都是 projection；它们可以延迟、丢失通知或重建，但不能反过来替代 transcript 判断下一步。

数据权威性增长形态故障后怎么处理
agent_transcript_events / JSONL会话事实只追加，按 session sequence不覆盖旧事件；从它重放上下文和终态
agent_runs查询投影一行运行摘要从 transcript 重建；不要用它判断工具是否发生
agent_run_steps查询投影每个模型/工具步骤一行用 event ID 做幂等 step ID，允许重放
stream delta / UI status瞬时呈现高频、可丢失重连或最终消息补偿；不作为恢复依据
inbox / session inputs待处理工作状态带 owner、lease、attempts按到期条件接管；确认必须命中当前 owner
事件不是“日志字符串”每条事件有 ID、session sequence、turn、type、timestamp 和结构化 payload。恢复依赖事件类型与相互关系；仅凭一行 error message 推断状态是不安全的。

四层处理权保护四种不同对象

所有权层次不能互相替代。Inbox 只能保证入口任务由一个 worker 处理；Session lease 才保证同一会话的上下文串行；工具 bulkhead 限制 fan-out；输入 claim 则保护追加消息不会被多个 worker 同时消费。

保护对象实现没有这一层的风险所有权丢失时
Slack eventslack_event_inbox 的 event_id、status、claim_owner、claim_until平台重投递产生多条回复旧 handler 停止，不 Complete/Fail 覆盖新 owner
Session turn本地 mutex；Hosted PostgreSQL advisory session lease两个 turn 从同一旧历史分叉不能再追加事实；新 owner 从 transcript 继续
Pending inputagent_session_inputs 的 sequence、owner、claim_until、ack追加消息重复进入或被确认两次Ack/Release 零行返回 claim lost，调用者不能假设成功
Tool fan-outMaxParallelToolCalls + 工具内部上限 + read/write lock模型输出制造无界 goroutine 和下游请求随 context 取消；已开始调用仍按未知副作用处理

Session lease 的语义是“保护完整执行期间的会话”，不是只在写 transcript 时短暂上锁。Hosted 实现为 advisory lock 绑定到专用数据库连接；GuardedSessionLease 每两秒确认连接仍可用，失去确认就取消执行上下文。

Hosted 如何给事件分配严格顺序

PostgreSQL transcript append 在事务内按 session 获取事务级 advisory lock，读取该 session 当前最大 sequence，再插入下一个序号。不同 session 仍可并行；同一 session 的 append 顺序由数据库提交事实决定。

  1. 开启事务并锁定 session。锁键由 session ID 稳定 hash 得到；使用 64-bit hash 避免高流量 session 因 32-bit 碰撞而不必要串行。
  2. 读取 MAX(sequence) + 1。空会话从 1 开始；AppendBatch 为同一 session 一次分配连续区间。
  3. 编码并写入 JSONB。event_id 是全局去重边界，session_id + sequence 是回放顺序边界；字符串中的 NUL 会被替换以满足数据库约束。
  4. 提交后再发布。sink 收到事件时，权威数据已经提交。sink 丢失只意味着需要 replay，而不是 transcript 丢失。
Append 成功不等于下游动作成功它只证明这个 canonical event 已经提交。如果 event 描述的是 ToolCallStarted，含义仍然是“执行边界已进入”，不是“外部 API 已完成”。

Local 如何用 JSONL 保持可恢复

Local profile 没有 PostgreSQL，每个 session 使用目录下的 events.jsonl。进程内 mutex 负责同一进程，.events.lock 的 OS file lock 负责同一台机器上的其他进程；目录为 0700，文件为 0600。

单条追加
取得文件锁，读取并修复尾部，追加完整 JSON 行，Write 后 Sync，再释放锁。
尾部半行
如果进程退出时最后一行未写完，loadAndRepair 截回最后一个完整偏移；这是可修复的 crash residue。
中间坏行
已经换行结束却无法解析时直接报错，不跳过；静默跳过会改变权威历史。
批量追加
临时文件写全并 Sync，关闭后原子 rename；分叉不会暴露半份会话。
会话 ID
使用受限字符集和长度，避免把路径分隔符或任意输入带入本地目录。

派生投影怎样在丢失通知后恢复

AsyncSink 只承载可重建投影，队列有界。队列满时它丢弃通知并累计 dropped，发送合并的 shed 信号；它不会为每条事件创建脱离控制的 goroutine，也不会让 canonical append 等待慢投影。

投影事件RunSink 如何使用幂等依据
TurnStarted创建/更新 run，保存 user、surface、model、tracerun ID = TurnID
ModelCompleted / Failed记录模型步骤、usage、finish reason、错误和首 token 延迟step ID = event ID
ToolCallCompleted / Failed记录工具名称、耗时、错误和截断信息step ID = event ID
Turn terminal更新 status、termination、error、duration、final hash按事件重放并重新计算
ModelStreamed可用于 first token 的临时观测，不作为 durable step丢失不影响最终消息和恢复

运行主记录不能塞入不断增长的 steps 数组作为唯一存储；当前 schema 将 run 与 run_steps 分开，避免每个新步骤都重写整个 aggregate，也避免并发投影互相覆盖。

三个最关键的崩溃窗口

工具已经修改外部系统，进程在保存结果前退出

已知transcript 中有 ToolCallStarted，但没有 ToolCallCompleted/Failed；外部副作用可能已经发生。

恢复写入 execution_interrupted 的工具失败结果，让下一轮模型先查询上游；不自动再次派发。

边界只有工具把稳定 ExecutionID 传给支持幂等的下游，并且能查询结果，才可以建立更强保证。

工作进程还活着，但 SessionLease 续期失败

已知新 worker 可能已经获得会话处理权；旧 worker 继续写入会制造两个 owner。

恢复Guarded lease 取消旧 context；旧 worker 不再追加或标记终态，新 owner 依据事件对账。

边界只在“写数据库成功”时检查 owner 不够；执行中的模型和工具也必须监听同一取消信号。

模型已经输出文字，随后流连接失败

已知入口可能已经展示了首段内容，完整 response 或 terminal 可能尚未落盘。

恢复ResilientClient 看到 output committed 后禁止 retry/fallback 拼接；入口保留已展示片段并记录投递状态。

边界运行完成、stream sink 收到、Slack 最终消息创建是三个不同事实，不能合并成一个 status。

恢复流程：先对账，再继续

  1. 确认谁拥有当前工作。查看 session lease、inbox claim、input claim 的 owner 与 expiry；没有 owner 不等于没有副作用。
  2. 读取 canonical transcript。按 session sequence 找 turn、step、model request、tool call 和终态，不以 runs 行的 status 作为唯一依据。
  3. 补齐未收敛的逻辑请求。ModelRequestStarted 无 completed/failed 时记录 ModelRequestUnknown；ToolCallStarted 无结果时记录 execution_interrupted。
  4. 只重做有安全证明的动作。模型临时错误可在未提交输出时重试；已完成 tool result 复用；外部 write 先查询或人工确认。
  5. 重建投影。从 transcript replay RunSink、trajectory 和指标；不通过删行或手改 runs 来“修复”源数据。
  6. 最后处理积压。恢复 inbox/input 后观察 attempts、dead-letter、lease expired 和队列深度，再逐步放量，避免恢复任务造成二次洪峰。
恢复的成功标准

不是“页面显示绿色”，而是：每个受影响 turn 都能定位到一个 owner 或终态；未知外部动作被显式标记；canonical sequence 无断裂；projection 可以从源事件重建；重复动作有上游审计或人工结论。

状态相关的生产推演

投影队列满了，能不能让模型暂停等它？

结论不应该。投影是可重建的派生层，反压 canonical execution 会把健康请求和慢观测耦合在一起。

要做监控 dropped/shed，随后从 transcript 重建；如果重建很慢，优化 projection store 或拆分队列，而不是取消事件事实。

数据库里 sequence 看起来不按 wall clock 排序

结论sequence 表示同一 session 的提交顺序，不是每个 goroutine 开始执行的时间。并行工具的 started 事件可能先后竞争，结果写回则按模型调用顺序。

要做用 event timestamp、trace span 和 tool duration 还原并发时间线，不要把 sequence 当成全局物理时钟。

清理 stuck processing 行能不能快速恢复？

风险如果健康 worker 只是慢，手动清 owner 会让两个 worker 同时处理；如果旧 worker 仍能访问外部系统，重复副作用会放大。

要做遵守 claim_until 和 owner-checking 的接管流程，先确认旧 owner 已取消或租约确实过期，再使用 recovery。

为什么一个 pending_input 不能被任意线程回复？

原因等待输入是带用户身份的会话状态。Runtime 的 WaitingForInput 会校验最新终态和原用户，防止另一个人把数据写入正在等待的工作流。

要做入口保留 session/thread/user scope；连接授权后的 continuation 也要重新建立正确作用域。
