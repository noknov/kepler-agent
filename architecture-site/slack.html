ADAPTER / SLACK

Slack 接入

Slack 是共享执行核心之外的一层适配器。它验证平台请求、把消息线程映射为会话、整理附件和追加输入，再将 Core 产生的事件投影为 Slack 回复。模型循环、工具调度和终态判断仍由 Core 完成。

适配器的输入输出契约

Slack 输入Core 契约边界
team、channel、thread、user身份与执行作用域平台标识只作为作用域数据，不进入 Runtime 控制流
event_id稳定请求来源用于入口幂等，不替代会话事件序号
消息、历史、附件统一内容块外部文本始终是不可信用户内容
线程中新消息追加输入源先持久化，再在稳定执行边界加入
交互按钮带用户身份的控制输入动作值必须能指向具体 turn 和 tool call
流式消息接口事件接收器呈现失败不改变 Core 中已经确认的执行事实
入口目标：Slack HTTP 请求只负责认证、规范化和入队，不能把“平台已经回复 200”解释成“模型已经完成”。执行完成与消息投递是两个独立的状态。

HTTP 接收：原始字节是签名边界

  1. 限制请求体。先读取有限大小的原始请求体，防止异常 payload 让入口耗尽内存。
  2. 检查时间窗口。拒绝过旧或未来偏差过大的时间戳，避免重放旧签名请求。
  3. 验证 HMAC。签名针对原始字节计算，使用常量时间比较；不能先解析 JSON 再重新编码。
  4. 解析事件类型。只把支持的 mention、message、file_shared、reaction 等事件交给 Handler；忽略 bot 自己的消息，避免回环。
  5. 按事件编号持久化。相同 event_id 收敛为一条 inbox 记录；写入成功后 HTTP 生命周期即可结束，Worker 再负责长执行。
失败点对 Slack 的响应对系统的事实
签名或时间非法拒绝请求不创建会话、不入队
JSON 不完整或事件不支持按入口策略确认或拒绝记录解析/永久错误，避免无限重试坏 payload
数据库不可用不能安全确认接收让平台重试或由入口层报告入队失败
已存在 event_id视为已接收不再创建第二个执行

事件路由不是“所有消息都启动新请求”

事件路由生产注意
频道 mention清理 bot mention，按频道权限创建或续接线程会话无权限只返回拒绝提示，不把原文送入 Core
私信新消息创建会话；线程回复优先作为已有会话输入bot、自身消息和非用户 subtype 要过滤
频道线程回复只有受支持线程、权限和非空内容才进入会话不要把无关频道聊天误接入 agent
file_shared私信场景下，按消息时间戳找到线程并转为内容块没有消息时间戳时等待对应 message.file_share 事件
reaction_added记录与运行/消息的反馈关联反馈不应改变已经完成的执行事实

频道、消息线程、用户和团队共同构成外部作用域；内部使用稳定的 session ID。event_id 标识入口请求，turn ID 标识一次执行，transcript sequence 标识会话内顺序，不能用一个 ID 代替三种语义。

线程与会话的连续性

首次处理时，适配器读取有限历史并转换为内部消息；之后的事件从会话记录继续。若会话已有活动执行，后续消息不会并发启动另一个相同 session 的 Runtime，而是按模式进入 steering 或 queue。

steering 只在模型判断前或最终答复确认前加入，不打断已经开始的一批工具调用；queue 则在当前 turn 结束后创建下一次执行。输入的认领者、确认者和过期恢复都由持久队列记录控制。

附件不是一个可以直接塞进 prompt 的 URL

  1. 确认来源和权限。只处理当前用户可访问的文件；私有下载地址和访问令牌不得进入模型上下文。
  2. 检查类型和大小。受支持图片转为图片内容，文本/Markdown/JSON 等受控提取，其他类型形成明确的不可用信息。
  3. 保存可追溯引用。内部内容块保留文件名、类型和稳定引用，下载失败要保留分类错误而不是伪装成空附件。
  4. 估算上下文代价。图片、提取文本和文件描述都占用上下文预算，过大时交给投影/压缩策略处理。
安全边界：模型可以知道“有一个用户上传的图片/文件以及它的受控描述”，不应获得可直接复用的 Slack 私有下载凭据。

按钮和审批必须回到具体执行事实

运行请求工具批准时，Slack 状态消息携带 turn_id 和 tool_call_id。用户点击批准或拒绝后，Handler 验证动作值，使用当前用户身份构造新的输入记录，再进入会话输入队列；它不是直接从 HTTP handler 调用工具。

步骤为什么这样做
Core 写入 approval_requested先记录等待的是哪一个具体工具调用
Slack 显示批准/拒绝控件把不可变的 turn/call 标识放在动作值中
用户点击后入队审批和普通输入共享顺序、租约和恢复机制
Runtime ResolveApproval按 session、turn、call 和 user 校验，防止旧按钮批准另一次执行
继续或终止结果仍写入 transcript，Slack 只是状态投影

流式回复和最终回复是两条投递路径

控制流事件
turn、工具、计划和审批状态更新 Slack session status；委派报告等内部事件不直接显示为用户文本。
首次可见文本
缓冲跨片段脱敏后的 assistant 文本，只有出现第一段非空可见内容时才建立 Slack 原生流。
节流追加
按时间或最小字符数合并更新，避免每个 token 都触发平台 API。
流式失败
标记投递失败但保留 Core 的完整答案；结束时回退到普通消息。
消息过长
分段发送并维护代码围栏状态，避免 Markdown 语义跨段损坏。
结果不确定
Slack API 与数据库没有共同事务；超时后先查询既有消息关联或稳定 client_msg_id，不能直接重复外部写入。
状态执行权威事实用户看到的表现
工具阶段无文本Runtime 仍在执行可以只有 processing 状态，不创建空白流
流成功更新文本 delta 已被适配器接受看到逐步增长的回复
流启动未知可能已在 Slack 创建消息不得盲目创建第二条，完成阶段先查询或修复
Core 已完成、投递失败turn_completed 已落盘管理侧显示 delivery error，重试投递而不是重跑模型

入口和投递的真实故障场景

平台重试同一事件

现象 Slack 因为入口超时又发来同一个 event_id。

正确路径 inbox 唯一键使第二次只得到“已接收”的结果；不要再次创建 turn 或发送第二次初始回复。

核对 event_id、inbox 状态、session ID 和 turn ID 是否一一对应。

流启动请求超时

现象 Slack API 没有返回明确结果，但请求可能已经在服务端生效。

正确路径 将启动视为未知结果，结束时查询消息关联；只有能证明未创建时才走普通消息补偿。

核对 client_msg_id、channel/thread、run 的最终消息关联和投递日志。

用户点击旧的批准按钮

现象 原 turn 已取消或已经进入另一个等待点，旧控件仍留在频道里。

正确路径 以 turn_id、tool_call_id、session 和用户身份校验；不匹配则忽略或提示控件过期。

核对 是否把按钮动作直接当成“当前工具批准”，绕过了 Runtime 校验。

消息有附件但文件事件先到

现象 file_shared 没有足够的消息线程信息，无法安全映射会话。

正确路径 不猜 session；等待包含消息时间戳的事件或通过补偿读取完整消息。

核对 附件是否重复入队、私有 URL 是否泄露到上下文和日志。
