Slack 接入

Slack 适配器验证平台请求，将线程和消息映射为托管会话，并投递执行结果。模型循环和工具策略由共享核心与托管产品配置负责。

输入与输出

输入适配器处理输出
签名请求按原始请求字节验证签名与访问范围可信平台身份和事件
消息与线程映射用户、频道、线程和会话规范化执行输入
执行事件合并流式更新并管理最终消息Slack 回复与关联记录

请求验证与持久接收

网关验证 Slack 请求签名和配置的访问范围。事件在进入工作进程前写入持久收件箱。平台事件去重与会话执行锁分别处理重复投递和并发执行。

会话用户、工作区和线程身份由入口传入。知道 session ID 不能替代 Slack 身份验证。

消息路由

入口按事件类型、提及和线程状态决定新建对话、继续会话或处理控制动作。当前 Slack 产品还可安装代码审查路由。Web 和本地 CLI 不因此具有相同路由。

支持的私信和频道行为受当前访问策略及具体工具约束。不能把事件订阅存在视为任何用户都能使用对应能力。

附件处理

附件需要补齐消息和线程上下文，再通过授权路径读取。文件事件缺少映射信息时，入口不能猜测会话。私有文件 URL 和凭据不应作为公开日志输出。

附件在原执行中的可见性与其是否长期保存分别判断。恢复后的记录不能声称重新读取了未保留的原始图片。

审批与控制动作

按钮、停止和补充输入必须匹配请求身份、会话、执行及具体等待点。旧控件不能作为当前工具的通用批准。

GitHub PR 审批工具具有独立的允许项与原始请求范围。共享频道确认不授予合并、评论或其他未启用操作。

流式与最终投递

适配器使用 Slack 的 start、append 和 stop stream 接口合并文本更新。最终答复可能需要替换流式消息或修复已知消息。

启动请求结果未知且没有消息标识时，不能直接再发一条来假设原请求失败。投递确认与执行结果分开保存。

重复事件与未知投递

情况处理边界
平台重发同一事件按入口事件身份去重
旧审批按钮按原调用和当前状态重新校验
投递请求超时区分明确拒绝与结果未知
执行完成但回复失败修复投递，不重跑模型与工具
