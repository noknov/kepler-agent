Slack 接入

Slack 负责把平台消息转换为托管任务，并把执行结果投递回对话。它需要处理验签、重复事件、线程身份、附件和流式消息。共享执行器负责分析与工具调度，但不会替入口完成这些平台工作。

输入与输出

一条 Slack 消息同时包含内容和平台上下文：谁发送、在哪个工作区和频道、是否属于已有线程，以及是什么事件。入口先验证这些信息，再决定怎样映射为内部会话和执行输入。

例如，用户在线程里要求继续调查登录问题，适配器需要找到原会话；用户另发一条根消息，则可能建立另一段对话。只把文字交给模型而丢掉线程与身份，会让后续权限和回复位置失去依据。

输出也需要适配。执行器产生的是模型文字、工具生命周期和终态，Slack 适配器将其转换为状态更新、流式文本和最终回复。界面控件不直接拥有执行权限。

请求验证与持久接收

网关使用收到的原始请求字节验证签名，再检查配置的用户和频道访问范围。不能先重新编码请求体，再用变化后的字节验签。

通过验证的事件进入持久收件箱，工作进程随后认领。这样入口可以尽快确认接收，而不必等模型调查完成。平台因超时重新发送同一事件时，事件身份用于去重。

这只能解决入口重复投递。用户重新发出另一条相似消息，或者同一任务内部重复执行工具，属于不同问题，需要对应的会话与调用规则。

消息路由

事件类型、提及方式、线程状态和当前产品策略共同决定处理路径。新任务、线程续接、补充输入、停止和按钮动作不能都视为“创建新执行”。

当前 Slack 产品还可以安装代码审查等工作流路由。例如，一条明确的 PR 审查请求可能进入特定的调查组织流程。这个路由属于 Slack 产品配置，不是所有入口共用的默认行为。

平台订阅了某类事件，也不代表任何用户都有对应能力。频道成员关系、入口允许范围和工具权限都要分别成立。

附件处理

附件通常需要额外的读取步骤。入口要先知道文件属于哪条消息和哪个线程，再通过授权路径获得内容。一个文件事件先到达时，可能还没有足够信息确定会话；这时不能随意猜一个 session。

附件的私有 URL 不是公开证据链接，也不应直接输出到日志。图片可以在当前执行里提供给模型，但用户图片是否长期保留，还要看持久化规则。恢复时只有“曾经有图片”的说明，不能当作原图仍然可用。

审批与控制动作

批准按钮必须绑定某个具体等待点，包括用户、会话、执行和工具调用。用户点击旧消息上的按钮时，当前执行可能已经取消，或正在等待另一项操作。入口需要重新核对这些关系。

停止动作也必须对应目标会话和执行，不能让一条无关线程控制另一段工作。用户确认表达的是对具体操作的选择，不会扩大服务端工具允许列表。

GitHub PR 审批工具还有自己的原始 PR 范围与头部版本检查。一次确认不能被解释为允许合并、评论或处理另一个 PR。

流式与最终投递

模型会陆续输出文字，Slack 则通过开始、追加和停止流式消息等 API 展示。适配器需要合并更新，避免每一个小片段都变成一个并发请求，也不能让慢投递直接阻塞模型回调。

最终答复不一定只是流式文字的继续。如果最终内容修订了前面的文字，适配器需要修复已有消息。已知消息 ID 时，可以针对该消息补偿，而不是再发一份可能重复的答案。

说明示例

消息创建结果未知

假设创建流式消息的请求已经到达 Slack，但响应丢失，应用没拿到消息 ID。此时无法仅凭超时确定消息没创建。

立即再发普通消息可能产生两份回复。系统应保留未知投递状态，并按消息关联或可核对证据处理。示例说明失败窗口，不代表一次实际 Slack 请求。

执行事件和投递记录分开保存。模型答复已经完整保存后，修复的是消息投递，而不是重新请求模型生成另一份结论。

重复事件与未知投递

重复事件按入口事件身份处理；旧控件按原调用与当前等待状态处理；未知投递按平台结果处理。这三类问题看起来都可能表现为“用户没看到正确回复”，但恢复动作不同。

排障时需要同时记录入口 event ID、会话与执行标识、线程位置和投递关联。入口确认接收只证明任务被接住，不能作为最终消息已发送的证据。
