工具与策略

工具是应用真正接触文件、命令和外部服务的位置。模型提出调用意图，执行器决定这次调用是否允许、何时启动、如何记录结果。可见性、权限和实际效果需要分别检查。

工具声明

工具声明向系统描述一种能力。名称和参数让模型知道怎样提出调用，效果声明让策略知道它可能读取、修改或访问哪些资源，并发属性说明能否与其他调用安全重叠。它们不是同一项设置。

例如，一个工具名为“检查配置”，实际实现却会修改文件，就不能只因名称听起来只读而按只读处理。执行策略需要依据效果和真实目标，工具实现还要履行自己声明的行为。

作用域（scope）则来自服务端可信的调用身份，包含用户、会话和工作区。模型可以选择业务参数，但不能通过填写另一个 user ID 获得那个人的凭据。

发现与激活

把所有工具定义一次性发送给模型，会占用大量上下文，也会增加选择难度。因此部分工具默认延迟提供。模型先搜索目录，取得名称和说明，再申请激活确切工具。

搜索只查目录，不执行工具，也不会因检索结果匹配就授予权限。激活只是把定义加入本次执行可见目录。执行器还要检查新增定义和确认结果能否纳入上下文；容量不足时保留原目录。

说明示例

找到工具与允许调用

模型可能找到一个读取代码的工具，也找到一个写入外部系统的工具。两者都出现在搜索结果，不表示两者都能执行。

真实调用时仍需检查当前用户、目标资源、效果和策略。目录告诉模型有哪些能力，策略决定这个请求能否使用它们。

调用流程

模型返回完整工具请求后，执行器先查找该调用的已保存结果。恢复时如果结果已经存在，就不重新访问外部服务。没有结果时，才进入后续检查。

  1. 识别工具和调用，解析参数；工具实现验证边界值与业务前置条件。
  2. 结合服务端作用域解析真实目标，检查能力策略。
  3. 需要批准时，保存原调用和等待状态；拒绝时记录明确结果。
  4. 允许执行时，取得并发名额与对应锁，保存开始事件。
  5. 执行工具，保存结构化结果或分类错误，并处理结果大小。

当前系统没有覆盖全部工具的完整 JSON Schema 校验层。因此“参数符合模型看到的 schema”不能替代执行器或工具的实际验证。验证成功、执行开始和执行结果是三个边界。

授权与审批

托管产品的写能力由操作员允许列表和效果策略决定。用户确认是在已经允许的能力范围内批准具体操作，不会新增服务器权限。

本地产品还需要考虑工作区、敏感路径、操作系统沙箱，以及针对具体调用的批准。允许某一次操作不等于允许模型以后任意生成新参数。

说明示例

批准绑定的对象

假设用户看到并批准的是“对文件 A 执行某次修改”。等待期间，模型又提出对文件 B 的修改。B 不能继承 A 的批准。

恢复批准时要取回原始调用、参数和作用域，并重新检查当前策略。工具消失、目标改变或权限收紧后，旧批准也不能无条件继续执行。

文件、命令与网络边界

文件路径需要检查实际落点。workspace/allowed/file 看起来位于工作区，但父目录可能是符号链接，指向工作区外。已有目标需要解析实际路径，新目标需要检查已有父目录；之后还要检查敏感位置策略。

命令使用参数数组（argv）启动。这样不会把模型输出整体当成一段 shell 程序。但命令本身仍可能读写大量资源，或启动子进程，所以 argv 不是沙箱的替代品。

本地沙箱由 macOS Seatbelt 或 Linux bubblewrap 等操作系统机制实施。它限制进程可见的文件和网络。沙箱可用性需要在实际系统上验证，不能只检查程序名是否存在。

网络工具还需要检查协议、目标主机、解析地址和重定向。最初 URL 合规，不表示重定向后的目标也合规。凭据按授权目的使用，不能顺便放进任意命令的子进程环境。

并发与资源限制

多个读取操作通常可以并行，但涉及修改共享资源的操作需要更谨慎。执行器按声明选择读写锁：允许并行的工具共享读锁，其他调用使用写锁。同时还限制并发名额，并在创建执行 goroutine 之前取得名额。

提前取得名额，是为了防止模型一次提出大量调用时，先创建同样多的等待工作。否则即使下游实际并发有限，本机也可能被等待任务和内存占用拖垮。

工具内部仍可能再次并发。例如，一个“读取多文件”的工具内部可能同时请求很多路径；数据库连接池也有自己的上限。执行器的总名额不能自动约束所有下游资源。

锁只会执行声明。如果修改工具错误地声明为可安全并行，锁不能识别真实副作用。新增并行工具应验证实际重叠、取消和下游限流。

结果与证据

工具结果既是模型后续判断的输入，也是恢复时的证据。大结果需要控制大小，但控制大小时不能隐藏“不完整”这个事实。否则模型可能把没看到的部分理解为不存在。

当前结果受单项和批次总预算限制。截断通过结构化字段和模型可见说明表达；需要保留的大内容可以外置为受作用域限制的 artifact。后续再用引用补读，而不是把整份内容每轮重复发送。

例如，一份长测试输出可能包含大量通过项和最后的失败断言。仅保留前部并声称“测试通过”，就是错误使用截断结果。工具应保留明确的完成与错误信息，模型需要按引用读取相关原文。

当前工具输出截断和较早历史的上下文遮蔽发生在不同阶段。两者都需要说明内容范围，但不能假设任何缩短后的文本都能恢复成原文；是否保留取决于对应存储。

恢复与重复失败

工具已保存结果时，恢复可以复用结果。只有开始记录而没有结果时，系统保留中断或未知；它不会把同一外部写入自动发送一次来“试试看”。已经生成但未开始的调用则形成未执行结果。

另一类问题是模型反复发起同样失败的调用。执行器在当前执行中按工具名称和规范化参数累计失败。达到阈值后阻止相同调用继续消耗；成功会清除该调用计数，执行结束后清理状态。

这个熔断保护的是继续执行能力和成本。它不证明工具安全，也不说明任务已经完成。被拒绝的调用不能被转换成业务成功。

MCP 连接与信任边界

MCP（Model Context Protocol）把工具放在外部服务中。路由器需要先建立会话、读取工具定义，再按调用身份发送请求。复用握手可以减少重复连接，但缓存必须与配置、凭据和作用域绑定。

例如，用户更新了集成令牌，后续调用不能只因为 user ID 相同，就继续使用旧凭据建立的会话。凭据变化、租户变化、有效期到达或传输错误，需要按规则重建或失效。

外部服务声明某工具只读，只是一项集成声明，应用并未因此证明它没有副作用。凭据范围、出站网络和执行隔离仍需要独立成立。连接重建也不构成重试未知写入的理由。
