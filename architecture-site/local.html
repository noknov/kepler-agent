本地 CLI 与 app-server

本地产品把工具运行在用户选择的工作区。交互式终端、无界面调用和 stdio app-server 使用同一本地执行机制，但输入连接、进程生命周期和呈现方式不同。

运行组件

Go 启动器处理参数和登录状态，并选择运行方式。交互模式启动终端界面，界面再通过 stdio 与 app-server 通信。无界面模式接收参数或管道输入，直接返回适用格式的结果。

app-server 是本地协议服务，不是另一套智能体。它把 thread 和 turn 操作转换为本地产品配置与共享执行器调用，发送消息与工具项目事件给客户端。

本地配置选择工具、文件边界、批准规则和 JSONL 存储。模型配置通过已经认证的网关启动路径取得，工具执行位置仍然是本机。

工作区与权限

--cwd 选择本地工作区。模型提出的相对路径、项目规则和命令都需要在这个范围内解释。用户的电脑上存在某个目录，不表示当前工具可以访问它。

读写根、敏感位置规则和操作系统沙箱共同限制工具。一次批准绑定具体调用与参数；不能因为批准过读取项目，就允许后续命令取得任意文件。

会话 JSONL 文件还需要跨进程的执行锁。两个本地终端同时恢复同一会话时，即使文件追加各自完整，也不能允许它们从同一旧历史同时推进。

登录与模型配置

CLI 登录用于建立与网关的认证关系，网关再提供适用的模型启动配置。用户的 GitHub 等外部集成连接，属于另一条授权路径，不能把二者混为一个“已登录”状态。

本地 TOML 主要配置执行限制、工作区读取范围、提示、技能和 MCP。它不是分发操作员模型密钥的替代渠道。当前启动方式也不能按旧示例假定存在直接选择任意 provider 或 API key 的参数。

排障时应先确定失败发生在登录、模型启动还是工具集成。三者都可能表现为“任务无法开始”，需要检查的凭据却不同。

协议与准入

stdio app-server 使用 JSON-RPC。客户端可以创建、恢复或分叉 thread，启动、补充或停止 turn，并接收 item 级消息。协议层负责这些操作的准入和身份关系，执行器负责实际步骤。

活跃执行数有上限。容量满时返回明确过载错误，客户端才能选择等待或有退避地重试。先无限接收再排到内存里，会使断开和关闭更难解释。

分叉复制的是一段会话历史，目标必须为空且未在活动中。它不能向另一个已经运行的会话直接追加历史，否则会破坏原会话的事件归属与执行顺序。

连接生命周期

stdio 连接拥有通过它接收的执行上下文。客户端退出、EOF 或输入错误后，服务需要取消活跃工作，并等待执行器完成必要事件清理，再释放工作区与存储。

这个行为与托管持久收件箱不同。托管入口已保存但尚未执行的请求可以按队列恢复；本地进程退出后，不能据此承诺所有还没处理的管道输入也已经保存。

说明示例

终端退出与已有工具

假设本地任务正在等待测试命令。关闭客户端会触发取消，但测试进程是否已停止、结果是否已保存，仍需由执行与进程清理规则处理。

已经写入文件的工具操作不会因为终端关闭自动回滚。恢复时要核对事件和实际文件，而不是只看上次终端有没有打印最终答复。

打包与验证

交互包包含启动器、app-server 和终端前端，三者的相对目录需要保持。普通包需要可用的 Node 运行时；便携包才另外携带运行时。打包脚本由部署仓库维护。

构建成功说明文件可以编译或打包，不说明所有用户交互和沙箱都可用。验证要分别覆盖 Go 逻辑、前端类型范围、输入与断开交互、协议边界，以及实际操作系统上的文件和命令限制。

尤其不能用无界面调用成功，代替终端界面可用的结论。它们共用执行核心，但接收输入和呈现结果的路径不同。
