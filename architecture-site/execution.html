CORE / EXECUTION

请求执行

执行器取得当前对话的处理权，读取已经保存的内容，组成模型需要的上下文。模型可以直接答复，也可以要求执行工具；工具结果写回对话后，模型继续判断，直到给出答复、等待用户或无法继续。这里的“循环”不是一个 while 语句，而是一组能够在进程重启后重新解释的状态转换。

一个 turn 多个 step一个 step 一次模型判断工具批次 先检查后执行终态 必须持久化

先分清五个容易混淆的对象

很多并发和重试问题，根源是把会话、请求、网络尝试和展示片段看成同一件事。Runtime 使用不同 ID 和不同事件类型把它们拆开。

Session / 会话连续对话和串行化边界。相同 session 的两个 turn 不能同时从同一份旧历史继续。
Turn / 请求从一条用户输入开始到明确终止。它可以跨多个模型 step，并可能暂停等待批准或用户补充。
Step / 轮次构造一次上下文并请求一次模型；若模型产生工具调用，则完成该批工具后进入下一轮。
Attempt / 尝试一次具体 provider 网络调用。一次逻辑模型请求可能包含 retry 或 fallback，但只能产生一个可供 Runtime 消费的完成结果。
Stream delta / 片段用于实时呈现的瞬时事件。它不是恢复单元；恢复依赖完整 assistant message、模型生命周期和工具结果。
判断恢复应该看哪一层如果进程退出，先看 turn 是否已经有终态，再看当前模型请求或工具调用是否只有 started 而没有 completed/failed。不要只看“最后一段文字”或内存里的 goroutine 状态。
01

执行器开始请求前的准备

入口只负责把外部协议转换成 TurnRequest。Runtime 负责确认身份字段、补齐 session/turn ID、取得会话所有权并将当前输入写入 canonical transcript。模型调用发生在这些事实建立之后。

  1. 确定请求属于哪段对话。入口提供稳定的 SessionID；没有时由执行器生成。TurnID 也可以由入口提供，用于重复提交返回已有结果。
  2. 确认当前内容是用户输入。没有角色时默认为 user；其他角色不会被接受为新 turn 的输入。历史导入只在 canonical session 为空时发生，并按普通不可信消息保存。
  3. 取得整段会话的处理权。本地运行使用进程内 session mutex；Hosted profile 再通过 PostgreSQL advisory lock 跨进程串行化。锁覆盖完整 turn，而不是只保护一次 append。
  4. 读取已有事实并做恢复对账。已经存在该 TurnID 的终态时直接重放结果；ToolCallStarted 没有结果时写入 execution_interrupted；ModelRequestStarted 没有收敛事件时写入 model request unknown。
  5. 建立 turn 边界。追加 turn_started 和 user_input。后续步骤、工具、追加输入和终态都关联同一 TurnID。
会话锁不是幂等键锁只能防止两个活跃执行者同时工作；它不能阻止用户重复发送一个新的 TurnID，也不能把外部 API 调用和 transcript append 变成一个事务。重复提交和外部副作用要分别处理。

主循环实际上是一台小型状态机

每一步都有“进入前检查”和“离开时事实”。任何返回路径都必须产生明确终态，或者留下足够信息让下一个 owner 继续对账。

阶段主要事件允许的下一步关键失败含义
Admittedturn_started、user_input投影上下文写入失败时不能发模型请求，因为输入没有进入权威历史
Step startedstep_started追加 steering、投影、请求模型取消在模型请求前发生，终止为 canceled
Model in flightmodel_request_started、attempt events得到完整响应或失败只有可重试错误才可换 attempt；重启后未收敛请求是 unknown
Tool batchassistant_message、tool_call_started完成/失败所有调用，按原顺序写结果单个调用可能已产生副作用；没有结果不能自动重做
Candidate final无工具调用的 assistant message两次检查追加输入收到新消息就继续下一 step，不把旧答复当作最终答案
Terminalturn_completed / failed / canceled释放锁、结束 turn-scoped catalog投影失败不应篡改 canonical terminal fact

“写事件”与“分发事件”是两个动作：Runtime 先调用 transcript store，成功后才向 projection sink 发布。sink 崩溃或变慢不能回滚已经提交的事实；投影应通过重放修复。

02

上下文怎样组成

每次模型判断前，执行器都会重新从权威事件中投影上下文。这保证刚完成的工具结果、刚追加的用户消息和新生成的摘要都会被纳入，同时避免入口自己拼接出另一套历史语义。

投影的取舍顺序

  1. 先为输出和工具定义留空间。可用输入预算是 MaxTokens 减 ReserveTokens；差值不合理时退回总上限，避免负预算导致不可解释的请求。
  2. 从最近有效摘要之后继续。CompactionCreated 带有 covers_through。边界缺失、为零或越过摘要事件自身时，投影器不会让它隐藏原始历史。
  3. 只映射会影响下一次判断的事件。UserInput、SteeringInput、AssistantMessage 和 ToolCallCompleted/Failed 进入；锁、步骤开始、运行投影和纯遥测事件不进入。
  4. 保持完整交互分组。用户输入、模型工具请求和工具结果构成不可拆分的 group。裁剪不会留下 tool call 却删掉 tool result。
  5. 从最新 group 向前保留。最新一组不能被丢弃；更早 group 在预算内加入。被移出的消息交给 compactor，并把最后事件序号记录成覆盖点。

当前输入和持久化输入的差异

模型请求可以暂时看到当前 message 中的图片，但 canonical transcript 不保留原始图片二进制；持久化时替换为说明文本。这样恢复不会依赖大段 base64，也不把敏感附件意外写入长期会话。若 provider 不支持某类图片，适配器在 dispatch 前去除并保留可解释的文字提示。

03

一次模型判断，底层可能包含多次网络尝试

Runtime 的逻辑边界是“这一轮有没有得到完整 Response”；ResilientClient 的边界是“某个 provider attempt 是否可安全重试或切换”。两者分开后，重启不会把一次网络失败误认为模型已经完成，观测也能区分逻辑请求和实际尝试。

错误类别默认处理思路不能做什么
transient / unavailable在 MaxAttempts 和 deadline 内重试；连续失败计入 provider/model breaker不能超过剩余预算继续发送
rate limited按延迟策略等待，必要时 fallback；尝试数和 token 成本仍要记录不能把 429 当作免费或无限容量
context limit通过 compactor 缩短 durable history，重新投影后再发一次不能只把当前请求字符串截断到半个工具交互
invalid / auth快速失败，修配置或凭据不能用重试掩盖错误配置
protocol / empty协议错误可在安全边界内重试；空内容按 MaxEmptyResponseRetries 处理不能把空响应当成 completed final answer
output committed停止 retry/fallback，保留已展示片段，终止为可诊断失败不能把两次模型回答拼在同一条消息中

首个非空文字 delta 是“输出已提交”边界。工具调用、usage 和 transport lifecycle 不会单独触发该边界，因为 Runtime 会等完整响应后才执行工具，入口也不会把这些事件当作 assistant 文本展示。

04

工具从模型请求到实际执行的完整路径

工具调用是从不可信模型输出进入真实系统的唯一入口之一。Runtime 把“模型想调用什么”和“系统是否允许、是否已经调用过、结果如何进入下一轮”拆成连续检查。

  1. 按 CallID 查找已有结果。恢复执行时，已有成功或失败结果直接复用，不再次派发。CallID 是 Runtime 去重边界；ExecutionID 供工具传给支持幂等的下游。
  2. 确认工具处于 active catalog。工具必须已注册，且是 eager 或已在该 session 激活。tool_search 负责发现和激活，不负责授权。
  3. 校验参数结构。注册时要求 object schema；执行前仍要由具体工具解析和检查参数。无效参数不应进入文件、网络或外部连接代码。
  4. 检查 exclusive 批次。需要用户输入等独占工具必须单独出现。混入其他调用时整批返回结构化错误，防止模型一边暂停一边先执行写操作。
  5. 作出权限决定。Policy 根据 descriptor effects、call scope、用户、workspace 和实际目标返回 allow、deny 或 require approval。描述和 surface 标签不构成授权。
  6. 取得并发名额，再启动执行。parallel 只允许明确安全的读取；MaxParallelToolCalls 在创建 goroutine 前作为 bulkhead。其他调用通过写锁串行化。
  7. 先记开始，再调用实现。ToolCallStarted 写入成功后才执行外部动作。工具有独立 timeout，panic、普通错误和空结果都会转成可解释的 ToolResult。
  8. 限制结果并按模型原顺序写回。并行调用可以先后完成，但结果写入和下一次上下文按照模型请求的顺序。单结果和整批都有大小预算。
ToolCallStarted 是有意留下的“危险边界”它证明执行器已经决定要调用，而不证明外部系统成功或失败。进程在这之后退出，恢复逻辑会写一个 execution_interrupted 的工具失败结果，让模型先调查，而不是假设“没看到结果所以没发生”。
05

工具结果的两层大小限制

大结果会同时伤害模型上下文、数据库写入、日志体积和 UI 响应。Runtime 先限制单个结果，再限制同一批结果的总量；若有 ArtifactStore，则把完整内容放在受作用域保护的附件中。

单个结果较小

原始 content 直接进入 tool message，模型可以完整读取。

单个结果超限且可 spill

完整 JSON 写入 artifact，模型收到有限说明、引用和大小信息。

没有附件存储

按 UTF-8 边界截断，追加明确的 truncated 标记，不伪装为完整结果。

多个结果合计超限

再次按 batch budget 分配，避免多个“各自合法”的结果一起淹没上下文。

结果被截断不会改变 canonical tool call 的身份和错误状态；它改变的是下一轮模型可见的 content。入口层的 Slack 长消息分段属于另一个展示问题，不能拿它解决模型上下文过大。

06

执行期间的新消息怎样加入

用户可能在模型仍工作时继续发消息。追加输入不是直接改写当前模型请求，而是进入 InputSource，在稳定边界被 claim、写成 SteeringInput、ack 后再参与下一次投影。

消息到达
Hosted 先写入 agent_session_inputs；Redis 只做快速唤醒，丢通知不会丢消息。
工作进程认领
按 session、kind 和 sequence 认领，带 owner/lease/attempts；处理权过期后可以被接管。
模型判断前
Runtime 原子取出待处理消息，写成 SteeringInput，再 ack。下一次上下文会看到它。
最终文字产生后
Runtime 在结束前检查两次；关闭输入源后再次检查，避免恰好到达的消息被漏掉。
工具执行期间
不插入当前工具批次。当前批次完成后再吸收消息，保持同一批工具基于同一意图执行。
为什么不实时打断每个工具打断会让同一批工具看到不同用户意图，还会产生“部分工具按旧意图、部分工具按新意图”的权限审计问题。稳定边界的代价是几十毫秒到一个工具超时的等待，换来可重放顺序。
07

一次处理怎样结束

结果触发条件恢复/呈现含义
completed模型返回无工具的最终消息，结束前没有新 steering可正常展示；若投影失败可从 transcript 重建
canceled用户中断、上层 deadline、session lease 丢失或服务关闭停止当前模型/工具；未完成外部调用仍按未知边界处理
pending_approvalPolicy 要求批准且当前没有同步 Approver保存具体 Call，UI 决定；批准时只执行已保存调用，不接受替换参数
pending_input工具明确要求用户补充信息只有被允许的用户回复才恢复该 session 的工作流
max_steps达到 MaxSteps，且最后一步已经完成停止，不额外发一轮“合成回答”请求，避免预算和状态不可预期
output_limit模型以 length 结束且没有工具调用保留已有消息并标记输出受限，不自动拼接第二次回答
empty_response空消息经过配置的空响应重试仍无内容作为可诊断失败结束，不把空内容当作用户答复
budget_exhausted剩余 deadline 不足以进行下一次有意义的尝试停止 retry/fallback，避免关闭期限内继续堆积工作
provider_circuit_open / fallback_exhausted提供方连续失败或主备路径均耗尽与普通 model_error 区分，便于容量和 provider 事故定位

终态事件使用 context.WithoutCancel 尝试写入，避免上层取消使恢复失去边界。若终态本身写入失败，调用者必须把它视为持久化故障，而不是报告“已完成”。

生产中最容易问错的几个问题

“模型超时了，重试就行吗？”

先看是否已经产生文字 delta、是否已经写入 ModelRequestStarted、剩余 deadline 以及错误的 typed kind。

结论未提交输出且属于 transient/rate-limited/unavailable/protocol 才能在预算内重试；首段文字后只能结束并保留已展示内容。

“ToolCallStarted 但没有完成事件，为什么不再调用一次？”

风险工具可能已经完成外部写入，只是进程在结果 append 前退出。再次调用会产生重复副作用。

结论先补写 execution_interrupted，让下一轮模型查询上游；能否安全重做取决于工具是否有幂等键和结果查询能力。

“MaxSteps 到了，为什么不再让模型写一段总结？”

原因总结本身也是一次模型调用，会突破既定 step、deadline 和成本边界；最后一个工具结果是否足够也未必已验证。

结论以明确的 max_steps 终态结束，让入口根据产品策略展示“达到执行上限”，或由用户发起新的 turn。

“同一个 session 的两个请求为什么不能并行？”

原因它们会从同一旧 transcript 投影出两个互不知情的上下文，工具顺序和追加输入也无法解释。

结论不同 session 可并行；同一 session 串行是会话一致性的必要条件，吞吐应靠多 session、入口队列和工具 bulkhead 调节。
