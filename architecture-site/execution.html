核心机制

请求执行

执行器取得当前对话的处理权，读取已经保存的内容，组成模型需要的上下文。模型可以直接答复，也可以要求执行工具；工具结果写回对话后，模型继续判断，直到给出答复、等待用户或无法继续。

01

执行器开始请求前的准备

执行器收到入口整理好的用户消息后，先确定历史范围和本次请求范围，再取得会话处理权并核对已有记录。完成这些准备后，才进入模型判断与工具执行的循环。

一段连续对话

保存从开始到现在的全部事件。它决定历史从哪里读取，也决定哪些请求必须保持先后顺序。

一次完整处理

从接收一条用户要求开始，到给出答复、等待用户、被取消或遇到无法继续的错误为止。

一次判断与执行

模型先根据当前信息判断。若它需要工具，系统执行后把结果放回上下文，再进行下一次判断。

进入模型循环之前

  1. 确定请求属于哪段对话。入口提供稳定编号；没有时由执行器生成。编号用于找到历史和识别重复请求，不要求读者理解它的源码格式。
  2. 确认当前内容确实来自用户。模型回复和工具结果不能伪装成本次新输入。
  3. 取得整段对话的处理权。同一进程用互斥锁；托管环境还使用数据库锁，防止两台工作进程同时从同一份旧历史继续。
  4. 读取已发生的事实。如果这次处理已经结束，直接根据记录恢复结果；如果上次停在动作中间，先把不确定状态说明白。
  5. 写下本次输入。从这里开始，后续模型判断、工具动作和最终结果都按顺序追加，形成可以恢复的完整过程。
会话级处理权后一次处理必须看到前一次已经写入的内容。若两个请求同时读取同一份旧历史，它们会各自生成一条互不知情的分支，工具动作的先后也无法解释。
02

上下文怎样组成

每次模型判断前，执行器都会重新从权威事件中投影上下文。这保证了刚完成的工具结果、刚追加的用户消息和新生成的摘要都会被纳入，同时避免入口自己拼接出不同语义。

系统说明怎样合成

入口传入多个片段。合成器先按片段种类和优先级排序，规范化空白，再连接成一条系统消息并计算内容摘要。若工具目录包含计划更新工具，还会追加计划使用说明。记录上下文投影时保存摘要值、估算字数、消息数量和工具数量，便于之后判断模型当时看到了哪一版说明。

旧消息怎样取舍

  1. 计算可用预算。总上下文上限减去为模型输出预留的空间；若配置不合理导致差值不大于零，则退回总上限。
  2. 找到最近一次摘要。摘要覆盖点之前的旧事件不再逐条加入，只把摘要作为较早背景放入。
  3. 把事件映射成模型消息。用户输入、执行中追加输入、模型完整消息和工具结果会进入；锁、步骤开始和运维状态不会进入。
  4. 按完整请求分组。一个用户输入、随后的模型工具请求及工具结果视为一个整体。裁剪时不会留下工具请求却删掉结果。
  5. 从最近一组向前选择。最新一组始终保留，更早的组只有在预算内才加入。被舍弃事件的最后序号成为下一次摘要覆盖点。

字数估算与自动压缩

估算器对英文字符、中文字符、消息角色、工具记录和图片分别估算占用。它的目标不是复刻某一家模型的精确分词，而是在模型请求发出前保守判断内容是否放得下。接近容量时，压缩器按完整用户请求切分，把较早部分概括成摘要；图片只保留文字说明，不把原始图片数据送进摘要过程。若模型服务仍然认为内容过长，执行器会进一步收紧预算，强制压缩后再尝试一次。

03

一次模型判断，底层可能包含多次网络尝试

执行器关心的是“模型有没有完成这次判断”。模型接入层关心的是“这次网络请求是否值得重试、是否需要换备用服务”。分开记录后，恢复逻辑不会把一次网络失败误认为整次判断已经完成，观测系统又能看清每次尝试发生了什么。

什么情况下会重试

只有明确属于短暂网络故障、请求频率受限、服务暂时不可用或可恢复协议错误的情况才会重试。重试次数、等待间隔和最低剩余时间都由运行配置控制。某个模型服务连续失败时会暂时停止向它发请求，成功一次后再恢复正常计数。

输出开始后的失败处理

一旦文字已经交给用户，继续重试或改用备用模型可能把两份不同答案拼在一起。因此首段可见文字是一条明确边界：它出现以前，系统可以安全地重试；它出现以后，系统只报告中途失败并保留已经展示的内容。模型完全没有返回内容时仍未越过这条边界，可以进行有限重试。

不同模型协议怎样接入

执行器只处理统一的内部消息。各模型服务自己的请求字段、工具块、图片、流式事件和错误格式由协议适配器转换。这样，上面的执行过程不需要针对每家模型重写。

04

工具从模型请求到实际执行的完整路径

  1. 复用已经完成的结果。先按本次请求和模型给出的调用编号查找记录。已经有成功或失败结果的调用不再次派发。
  2. 确认工具当前可用。工具必须已注册，并且处于立即公开状态或已在这个会话中激活。找不到时生成结构化错误交还模型。
  3. 检查独占要求。声明为独占的工具必须单独出现在本批请求中。如果模型把它和其他工具混在一起，整批都不执行。
  4. 作出权限决定。权限层返回允许、拒绝或等待批准。拒绝会形成工具错误；需要批准但当前没有批准器时，本次请求以“等待批准”正常暂停。
  5. 按工具属性调度。明确声明可并行的工具先取得并发名额，再共享读取锁；其余工具取得写锁。并发名额在创建 goroutine 之前取得，防止模型一次生成大量请求耗尽进程。
  6. 先记开始，再调用实现。每个工具可有独立超时。执行器捕获 panic、普通错误和空结果，并统一生成模型可见的错误结果，同时记录耗时与追踪编号。
  7. 限制结果并按原顺序记录。工具可以并行完成，但写回模型的顺序仍与模型请求顺序一致，避免并发时序改变语义。

权限判断依赖哪些信息

每个工具描述自身影响：只读、修改工作区、修改外部系统、需要高权限或访问网络。调用还携带用户、工作区、会话和入口提供的作用域。本地权限层会继续检查解析后的路径、符号链接、敏感文件和网络目标；托管权限层使用服务端配置与精确工具名决定。入口附带的文字标签不会自动获得写权限。

重复调用保护

除了用持久化结果避免恢复时重做，执行器还在单次活跃请求内记录相同工具名和参数的连续失败。达到阈值后阻止继续重复，防止模型陷入无效循环；请求结束时清除这份内存状态。若外部系统支持幂等编号，工具实现还可以使用执行器提供的稳定执行编号，形成第二层保护。

05

工具结果的两层大小限制

单个工具返回大量日志或文件内容时，不能让它独占整个模型上下文；多个工具各自不大，合起来也可能超限。因此系统先限制每个结果，再限制同一批结果的总量，具体上限由产品配置决定。

结果较小

正文直接保留在工具结果中，下一轮模型可以完整读取。

结果过大且有附件存储

完整内容写入附件存储，模型获得说明、有限预览和稳定引用。

整批仍超限

执行器在批次范围再次分配预算，保证并行工具不会一起淹没上下文。

Slack 最终回复过长由 Slack 入口分段发送，并在分段时维护代码块围栏闭合；它不会改变模型看到的工具结果。

06

执行期间的新消息怎样加入

用户可能在模型仍工作时继续发消息。本地交互可以使用内存收件箱；托管环境先把消息写入 PostgreSQL，再用 Redis 做快速唤醒。执行器只在稳定边界吸收这些消息：每轮模型判断前，以及模型准备给出最终文字后再检查两次。

消息到达
先持久化为待处理输入；写入成功才算被系统接收。
工作进程认领
取得一段有时限的消费权，数据库记录认领者和尝试次数。
执行器排空
把消息写成普通会话事件，然后确认消费完成。
模型已给最终答复
若此时发现新消息，当前执行轮次标为“收到追加输入”，继续下一轮模型判断，而不是立即结束。
输入需要单独处理
某些入口可以把它排到本次请求之后，作为新的请求处理。
工具执行期间暂不插入新消息那会让同一批工具基于不同用户意图执行，并使权限和结果顺序难以解释。稳定边界带来一点等待，但保住了可重放的顺序。
07

一次处理怎样结束

结果发生条件
正常完成模型返回最终文字，且结束前没有收到新的追加输入
用户取消用户要求中断，或入口失去继续处理的资格
等待批准工具需要人工决定，系统保存当前位置并等待答复
等待用户补充工具已经说明缺少什么信息，当前处理暂停
达到执行轮数上限模型持续请求工具，没有在限制内给出最终回复
输出被截断模型已经到达自身输出长度限制
模型请求无法继续可重试路径已经用尽、模型服务暂时停用或剩余时间不足

这些结果在事件记录中都有对应的内部状态值。具体名称集中列在源码索引页。
