委派执行

复杂工作可以拆成多个有边界的子任务。每个子任务使用同一套执行器，在独立会话中读取自己的上下文并留下完整记录；主任务负责选择分工、接收报告、核验证据并生成最终答复。

委派不是第二套 Agent Runtime

委派能力没有建立一套平行的模型循环。它为每个子任务创建独立请求，使用经过过滤的只读工具目录和明确的任务说明，再调用共享执行器。因此上下文投影、模型重试、工具调度、会话锁、记录和结束条件都沿用普通请求的契约。

边界：子任务的文字片段不会直接成为最终输出。主任务接收报告和审计信息，仍然负责判断报告是否可信、是否覆盖范围以及是否需要再次检查。

每个子任务都必须能独立验收

任务批次只接受能够独立执行的叶子任务。只写“检查一下”会把拆分成本转移给子模型，也使失败后无法判断缺的是范围、证据还是结论。

字段运行时要求缺失时的风险
稳定名称批次内唯一，用于关联结果和记录报告覆盖错位，主任务无法可靠汇合
角色限定观察角度，例如数据一致性、并发安全或接口兼容性多个子任务重复同一判断
目标说明要解决的具体问题，包含范围和目标文件子任务自由扩展，成本和耗时失控
边界限定文件、风险类型、外部系统和禁止动作读取越界或产生未授权副作用
交付物规定报告要包含证据、位置、影响和结论只返回“通过/失败”，无法复核
成功条件让主任务能判断是否覆盖所需范围正常结束被误解为问题已解决

运行时不固化一套角色，也不要求每次拆成相同数量。主任务根据变更范围和已有证据决定人数、角色和后续核验；任务说明本身也应记录，便于解释为何产生这批成本。

先等待并发名额，再开始计时

委派的生产难点不只在并发数，还在“任务什么时候开始计时”。调度器对总任务数、同时运行数、主任务剩余 deadline 和单子任务 timeout 都设上限；单个子任务的运行时限从真正取得 Worker 名额后开始，而不是从排队那一刻开始。

校验
拒绝空目标、重复名称、越界范围和不允许的工具；不要创建无法收敛的子会话。
等待并发名额
任务尚未开始模型请求，只消耗批次队列容量；主任务取消时，排队任务也要被移除或标为取消。
取得名额
创建子会话和请求，写入父子关联，然后启动共享执行器。
运行期间
子任务只能使用过滤后的工具目录；取消、父级 deadline 和会话失权都传给子执行。
结束
结果包含子会话、子请求、身份、结束原因、用量、报告和错误，且不把“有输出”当作“成功”。
汇合
主任务按稳定名称接收结果，决定直接使用、自己核验，或再启动有针对性的后续任务。
预算应限制什么为什么不能只限制模型 token
Fanout一次批次最多创建多少子任务任务说明、数据库记录、投影和报告都会随数量增长
Workers同时执行的子任务数每个子任务还会占模型请求、工具槽位和连接
Deadline批次和子任务的剩余时间排队、重试、工具等待都可能耗尽用户可接受延迟
Output单份报告和批次汇总的大小大报告会污染父上下文，增加压缩和费用

上下文隔离与共享输入

每个子任务拥有自己的事件序列，主任务只向它注入任务说明、必要的共享上下文和明确的输出格式。共享上下文应是已经确定的事实或摘要，而不是把父任务全部历史复制过去；否则并发任务会重复计费，也可能把互相推测的内容放大。

可注入内容用途注意点
父任务目标和范围让子任务理解为什么被创建必须标明这是任务说明，不是用户可执行命令
共享事实摘要避免每个子任务重复读取同一大文件摘要可能过时，报告仍要给出原始证据位置
只读工作区并行探索、代码审查、资料收集过滤 catalog，禁用写入、网络和再委派
父任务中间结论缩小检查范围标记为待验证，不应变成无来源事实

当前探索实现使用隔离的子 turn、子 transcript、父子链接和受限的读工具目录；子任务不直接向最终用户发布结论，也不再启动新的委派层级。

关联记录必须能解释成本与失败

每个子任务拥有自己的事件序列，并在创建时保存父任务关系。主任务不复制子任务的全部消息，只保存任务说明、完成状态、报告、用量和子记录位置；这样既能审计分工，也不会让多个长上下文互相污染。

记录位置保存内容查询用途
主任务任务批次、每项任务的身份与要求、子任务完成结果、汇合后的判断解释总体决策和最终输出
子任务自己的系统说明、上下文、模型尝试、工具调用、恢复事件和结束原因定位某个子任务为何慢或失败
运行查询视图父子关系、耗时、模型用量、错误、完成与取消按批次统计成本和吞吐
执行轨迹经过脱敏的提示、上下文、提供方尝试、工具和结束事实还原控制流而不扩大敏感数据暴露
不要把报告当作权威事件：报告是子任务对事实的解释；会话事件记录的是它实际走过的控制流。主任务需要在冲突时回到证据和事件，而不是让后写入的文字覆盖先前事实。

部分成功要有明确语义

子任务状态主任务应该怎么处理
completed读取报告并检查是否满足成功条件；完成不代表结论正确。
canceled / deadline标记该角度未覆盖，不把空报告当成“没有问题”。
model error / provider circuit保留失败类型和尝试信息；若该角度关键，缩小范围后重试或由主任务接管。
tool failure报告工具失败位置和影响；不能只返回模型生成的补偿性猜测。
报告为空或超出预算视为不完整交付，限制其进入父上下文的字数并重新确认目标。

汇合阶段应区分“所有任务都结束”“关键任务成功”“结果彼此一致”三个概念。最安全的默认是：对外输出前由主任务做一次范围检查，必要时读取原始位置或补跑最小验证，而不是盲目等待所有非关键任务。

生产中最容易出现的几个问题

一个子任务卡住，为什么不应该拖死整批？

现象 四个任务已经返回，剩下一个工具连接一直等待。

处理 单任务 timeout、父级 deadline 和批次最大等待时间分别生效；主任务收到明确的 partial result，再决定是否在关键结果缺失时补跑。

核对 看任务是否真正取得 slot、工具是否写入 started、子会话是否仍持有锁，不要只看“创建时间”。

报告说“已检查”，怎样判断它是否可信？

现象 子任务正常结束，但报告没有文件位置或只给一句结论。

处理 按交付物和成功条件判定为不完整；主任务回到证据位置或重新发一个更窄的只读任务。

核对 子任务的报告、工具调用和上下文裁剪记录是否一致，避免把摘要丢失误判为未发现。

并发扩大后，为什么成本和锁等待一起上升？

现象 Fanout 增大后模型调用更多，数据库连接池、投影队列和工具服务同时变慢。

处理 把 fanout、worker、模型并发和工具槽位作为一组预算调节，并限制报告进入父上下文的大小。

核对 比较每个子任务的排队时间、模型 token、工具耗时和数据库锁等待，而不是只看总 wall time。

父任务取消时，已经启动的子任务怎么办？

现象 用户停止了主任务，部分子任务还在模型或工具调用中。

处理 传播取消并停止创建新子任务；对已经写入 started 的工具保留未知/中断事实，不能假设外部副作用已经撤销。

核对 父任务结束原因、子任务结束原因、工具结果和租约状态是否都已落盘。

委派边界

主任务是唯一协调者

子任务不再拆分新的团队，也不直接向最终用户发布结论。

子任务默认只读

当前探索和代码审查只需要读取与分析；写入、网络、权限提升和外部副作用不随意传入。

报告需要再次判断

完成状态只说明子任务结束，不表示其中每条结论都已经被主任务验证。

并发保持有界

任务数量、同时运行数量、报告大小和截止时间都由运行配置限制，并接受主任务取消。
