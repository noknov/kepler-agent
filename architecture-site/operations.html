运行维护

队列、观测与关闭

托管服务把接收请求、认领工作、执行会话和查询运行状态分开。PostgreSQL 保存不能丢失的事件与队列状态，Redis 只负责快速唤醒，运行投影提供查询与指标；服务关闭时先停止接收新工作，再等待已经取得处理权的请求结束。

先分清控制面和执行面

Gateway 的职责是尽快验证并落盘，Worker 的职责是持有会话执行权并续期，Observability 的职责是读取投影回答查询。三者可以独立扩缩容；把它们合成一个同步 HTTP 请求，会把平台回调超时、模型延迟和工具副作用绑在同一个失败窗口里。

组件拥有的状态不应该承担的职责
Gateway请求认证、入口去重、收件箱写入、用户输入入队长时间持有模型或工具执行
Worker事件处理权、会话锁、turn 生命周期、工具执行把内存中的状态当作恢复依据
Observability运行/步骤查询、轨迹、费用与健康信息修改权威会话历史来“修复”展示结果
PostgreSQL收件箱、输入队列、会话事件、运行投影与审计关联替代模型或工具的实时流传输
Redis唤醒提示和短期调度信号充当消息唯一副本
判断标准：任何“Redis 丢了会不会丢消息”的问题，答案都应该是否定的；任何“数据库写成功但进程崩了能否恢复”的问题，答案都应该指向事件或队列记录，而不是某个 Worker 的内存。

Slack 收件箱：先接住，再交给执行者

Slack 可能因为响应超时或网络故障重复发送同一事件。入口用平台事件编号作为稳定去重键，把原始事件写入 PostgreSQL 收件箱。只有持久化成功后才确认接收；Redis 通知丢失只会让处理变慢，不会让事件消失。

  1. 原子认领。工作进程按到期时间取一批事件，并跳过已被其他进程锁定的行，避免多进程同时处理同一条收件箱记录。
  2. 租约续期。认领后记录处理者和期限；后台续期协程定期延长处理权。续期没有命中时，说明旧进程已经失权。
  3. 失权即取消。旧进程必须取消当前执行，也不能再把事件标为完成或失败；否则一个慢请求可能覆盖新进程的结果。
  4. 失败退避。临时错误延后到下一次可执行时间；无法解析的事件和超过尝试范围的事件进入停止自动处理的状态，并保留原因。
  5. 期限接管。进程退出后，恢复任务扫描过期租约，使事件重新可认领。恢复不是重放旧进程的内存，而是从持久状态启动新的处理尝试。

执行中的新消息使用独立持久队列

接收后续消息的进程可能不是正在运行该会话的进程。新消息先写入会话输入队列，Redis 再尝试通知当前执行者。执行器会在稳定边界查询 PostgreSQL；所以唤醒是优化，不是正确性条件。

写入
为消息分配会话内顺序并保存内容、来源和路由方式。
认领
当前执行者按顺序认领取正在等待、认领已过期或仍属于自己的消息。
加入会话
执行器把消息写成普通用户输入事件，使它进入下一次上下文投影。
确认
处理完成后按消息编号和当前认领者更新状态。
处理权丢失
确认或释放没有命中记录时返回错误，调用者不能把消息当成已经处理。

排队到当前请求之后的消息会在本次请求结束后建立新的请求。要求立即影响当前工作的消息，只在模型判断前或最终答复确认前加入，不打断正在执行的一批工具；这让工具调用与用户 steering 之间有稳定的顺序边界。

运行列表和步骤是可重建的投影

运行投影读取会话事件，把一次请求整理成便于查询的运行记录和步骤。运行记录保存模型、用户、入口、开始与结束、用量、费用、错误和最终消息关联；步骤分别描述模型尝试、工具、批准、压缩和其他阶段。

步骤逐条追加，不把不断增长的步骤数组反复写回运行主记录。异步投影队列拥堵时可以舍弃可重建通知并发出重建信号；运行投影可以重新读取会话事件恢复。会话事件写入失败时则不能继续假装本次动作已经保存。

费用与关联

模型适配器返回输入、输出和缓存用量。运行投影使用服务配置提供的费率计算估算值；没有提供费率时记录为零，不根据模型名称猜测价格。运行记录保存最终 Slack 消息的频道、线程和消息位置；发送恢复先查询这个关联，再使用稳定消息编号缩小重复创建回复的窗口。

轨迹回答“控制流走到哪里”

轨迹读取接口从会话事件重建提示和上下文生成、模型提供方尝试、工具执行、恢复动作和结束过程。默认结果经过脱敏，不返回消息正文、工具参数或任意元数据；需要业务内容时走受控的运行详情权限。

容量不是“Worker 数量”一个数字

一个 Worker 同时消耗数据库连接、会话租约、模型并发、工具槽位、上下文内存和外部 API 配额。扩容前要找出最先饱和的那一层；只增加 Worker，可能把延迟从应用内转移到数据库或提供方。

背压点必须有的动作
入口队列达到上限拒绝或延迟确认新事件，并记录可告警的原因；不能无限把请求堆进内存。

健康检查要回答不同问题

检查含义调度系统的处理
进程存活HTTP 进程仍能响应失败时重启进程
服务就绪关键依赖可用且服务没有进入排空状态只有就绪时发送新流量
工具健康工具依赖、连接和基础能力是否可用供管理页面诊断，不替代每次调用的错误处理
运行与费用指标请求数量、持续时间、错误、模型用量和估算成本用于监控、容量判断和故障定位

“进程活着”不等于“可以接新流量”，“模型可用”也不等于“某个连接的工具可用”。运行、指标和健康详情属于管理接口，需要管理凭据或受控的本地开发访问，不通过普通用户入口公开。

关闭是一个可观察的状态转换

  1. 进入排空状态。服务就绪检查开始失败，流量调度器不再发送新请求。
  2. 入口停止认领新工作。已经持久化但尚未认领的事件留在数据库，其他健康 Worker 可以接手。
  3. 等待正在执行的请求。仍持有处理权的工作继续运行并续期，直到完成或到达关闭期限。
  4. 关闭期限到达后取消。未完成请求通过上下文取消退出；没有完成的入口事件在处理权到期后重新可用。
  5. 停止后台任务并关闭依赖。停止投影、提醒、Redis 唤醒和连接维护任务，等待已经提交的写入返回，再关闭数据库与 HTTP 服务。
关键顺序：先摘流量，再停止认领；先取消执行，再释放会话；先让租约自然或显式到期，再让其他 Worker 接手。关闭日志要能区分“排空开始”“主动取消”“租约到期”和“进程退出”。
