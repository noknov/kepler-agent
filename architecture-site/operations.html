运行维护

队列、观测与关闭

托管服务把接收请求、执行工作和查询运行状态分开。PostgreSQL 保存不能丢失的事件和队列状态，Redis 用于快速唤醒，运行投影提供查询与指标；服务关闭时先停止接收新工作，再等待已经取得处理权的请求结束。

托管服务的进程分工

进程主要职责依赖
Gateway接收 Slack 和 OAuth 请求、代理 Web 流量、提供公开回调入口签名与登录配置、Worker 上游、连接回调
Worker认领 Slack 事件、组装托管产品、运行共享执行器、托管 Web 入口和工具能力PostgreSQL、Redis、模型服务、工作区和外部连接
Observability读取运行与步骤数据，提供指标、运行详情和工具健康信息运行投影与管理访问控制

接收 Slack 请求的 HTTP 生命周期不覆盖模型执行时间。Gateway 或 Worker 的入口处理函数完成验证和持久化后即可响应平台，真正的模型与工具工作由能够续期处理权的工作进程完成。

Slack 收件箱怎样处理重复投递和工作进程退出

Slack 可能因为响应超时或网络故障重复发送同一事件。入口用平台事件编号作为稳定去重键，把原始事件写入 PostgreSQL 收件箱。只有持久化成功后才确认接收。

  1. 工作进程原子认领一批到期事件。查询和状态更新在同一数据库操作中完成，并跳过已经被其他进程锁定的行。
  2. 认领后开始会话处理。事件记录当前处理者和期限；后台续期协程定期延长处理权。
  3. 续期必须验证处理者。更新没有命中时表示处理权已经丢失。旧工作进程立即取消执行，也不能再把事件标为完成或失败。
  4. 临时错误延后重新执行。下一次可执行时间按尝试次数计算；无法解析的事件和超过尝试范围的事件停止自动处理。
  5. 进程退出后由期限接管。没有完成的处理权到期后，恢复任务把事件重新放回可认领状态。

执行中的新消息使用独立持久队列

接收后续消息的进程可能不是正在运行该会话的进程。新消息先写入会话输入队列，Redis 再尝试通知当前执行者。Redis 通知丢失不会丢消息，执行器会在稳定边界查询 PostgreSQL。

写入
为消息分配会话内顺序并保存内容和路由方式。
认领
当前执行者按顺序认领取正在等待、认领已过期或仍属于自己的消息。
加入会话
执行器把消息写成普通用户输入事件，使它进入下一次上下文投影。
确认
处理完成后按消息编号和当前认领者更新状态。
处理权丢失
确认或释放没有命中记录时返回错误，调用者不能把消息当成已经处理。

排队到当前请求之后的消息会在本次请求结束后建立新的请求。要求立即影响当前工作的消息只在模型判断前或最终答复确认前加入，不打断正在执行的一批工具。

运行列表和步骤从事件生成

运行投影读取会话事件，把一次请求整理成便于查询的运行记录和步骤。运行记录保存模型、用户、入口、开始与结束、用量、费用、错误和最终消息关联；步骤分别描述模型尝试、工具、批准、压缩和其他阶段。

步骤逐条追加，不把不断增长的步骤数组反复写回运行主记录。异步投影队列拥堵时可以舍弃可重建通知并发出重建信号；运行投影可以重新读取会话事件恢复。会话事件写入失败时则不能继续假装本次动作已经保存。

费用怎样记录

模型适配器返回输入、输出和缓存用量。运行投影使用服务配置提供的费率计算估算值；没有提供费率时记录为零，不根据模型名称猜测价格。

Slack 消息关联

运行记录保存最终 Slack 消息的频道、线程和消息位置。发送恢复先查询这个关联，稳定的消息编号进一步缩小重复创建回复的窗口。

执行轨迹用于还原控制流

轨迹读取接口从会话事件重建提示和上下文生成、模型提供方尝试、工具执行、恢复动作和结束过程。默认结果经过脱敏，不返回消息正文、工具参数或任意元数据。

轨迹部分能够说明的事情
上下文一次模型判断使用了哪些事件范围、是否使用摘要以及发生了何种裁剪
模型尝试同一次判断包含哪些网络尝试、使用哪个提供方以及在哪里失败
工具调用何时开始、是否完成、是否由恢复逻辑补成中断
批准哪个具体调用等待决定以及最后采用的决定
结束请求因正常答复、等待、取消、限制或错误中的哪一种停止

健康检查分别回答不同问题

检查含义调度系统的处理
进程存活HTTP 进程仍能响应失败时重启进程
服务就绪关键依赖可用并且服务没有进入排空状态只有就绪时发送新流量
工具健康工具依赖、连接和基础能力是否可用供管理页面诊断，不直接替代每次调用的错误处理
运行与费用指标请求数量、持续时间、错误、模型用量和估算成本用于监控、容量判断和故障定位

运行、指标和健康详情属于管理接口，需要管理凭据或受控的本地开发访问。它们不会通过普通用户入口公开。

服务怎样停止接收并完成已有工作

  1. 进入排空状态。服务就绪检查开始失败，流量调度器不再发送新请求。
  2. 入口停止认领新工作。已经持久化但尚未认领的事件留在数据库，其他健康工作进程可以接手。
  3. 等待正在执行的请求。仍持有处理权的工作继续运行并续期，直到完成或到达关闭期限。
  4. 关闭期限到达后取消。未完成请求通过上下文取消退出；没有完成的入口事件在处理权到期后重新可用。
  5. 关闭数据库、缓存和 HTTP 服务。停止后台投影、提醒和连接维护任务，等待已经提交的写入返回。

常见中断点和恢复依据

中断位置已经保存的事实恢复动作
Slack 事件入队后、认领前收件箱等待记录任一工作进程在可执行时间到达后认领
工作进程认领后退出处理者和处理期限期限到达后重新排队或由恢复任务处理
用户后续消息写入后通知丢失输入队列中的消息执行器下一次轮询或补偿扫描读取
会话事件已写入、运行投影未更新权威会话事件投影器重新读取并生成运行与步骤
Slack 回复请求超时且结果不确定稳定请求和消息编号、可能已有的消息关联先查询已有投递，不直接创建另一条回复
排空期限内没有结束请求开始和已经完成的步骤取消旧执行；新进程按会话事件和队列处理权恢复
