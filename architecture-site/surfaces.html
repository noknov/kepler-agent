产品入口

Slack 和 Web

Slack 和 Web 在服务端运行相同的托管产品配置。两者使用同一个执行器、模型服务、工作区、会话事件存储和服务端权限策略；身份确认、对话建立、输入整理和结果呈现分别由各自的入口实现。

入口交给执行器的内容

入口完成协议处理后，向托管产品提供稳定的会话、当前请求、用户消息、系统说明补充、工具作用域和执行中的输入来源。Slack 事件原文、HTTP 请求对象、浏览器 cookie 和页面状态留在入口层。

执行所需内容SlackWeb
用户团队安装和 Slack 用户经过 OpenID Connect 验证的团队与用户
连续对话频道和消息线程确定按当前登录用户保存的 Web 对话
当前请求Slack 事件编号提供稳定来源客户端请求编号经过稳定转换
输入消息文字、线程历史和经过检查的附件浏览器提交的文字

输出接收器原生流式消息、普通消息和线程状态SSE 订阅与当前回复快照

Slack 请求先验证和持久化

  1. 读取有限大小的原始请求体。签名针对原始字节计算，入口不会先把 JSON 解析后重新编码。
  2. 检查请求时间。时间窗口之外的请求被拒绝，降低旧请求被再次发送的风险。
  3. 验证签名。服务端使用 Slack 签名密钥计算 HMAC，并采用常量时间比较。
  4. 识别平台验证或普通事件。平台验证立即返回所需内容；普通事件进入后续处理。
  5. 按平台事件编号写入收件箱。相同事件重复到达时落到同一条持久记录。写入成功后 HTTP 请求即可返回。
  6. 工作进程认领并续期。模型执行脱离原始 HTTP 请求。认领、失败重试和工作进程退出后的接管由收件箱状态控制。

Slack 消息怎样建立会话

工作进程取得事件后读取团队安装与用户信息。频道和消息线程共同确定连续对话；同一线程里的后续消息因此进入同一份事件记录。平台事件编号作为当前请求的稳定来源，用于识别重复处理。

首次历史

本地还没有会话事件时，入口从 Slack 读取有限的线程历史。用户消息和机器人消息转换成内部消息，外部文字始终作为不可信对话内容，不会因为来自历史而变成系统指令。

附件

入口解析当前消息和历史中的附件，检查文件类型和大小，再决定直接形成图片内容、提取文字还是通过大文件工具访问。下载使用当前团队安装的访问能力，结果进入执行作用域，不把原始 Slack 文件对象交给模型。

后续消息

线程有活跃请求时，入口根据输入路由决定把消息加入当前执行，或排在当前请求之后单独处理。两种路线都先写数据库，Redis 只负责更快唤醒当前工作进程。

Slack 回复从文字片段到最终消息

执行开始后可以先更新线程状态。模型产生第一个可见文字片段时才建立 Slack 原生流，因此只调用工具的早期阶段不会产生空白回复。

文字片段到达
跨片段脱敏器保留尚不能确定安全的尾部，确认安全的文字再进入发送缓冲。
建立原生流
使用当前频道和线程创建一条流式回复，后续片段追加到同一消息。
流式接口失败
保留已经生成的完整答案，结束时改用普通 Markdown 消息；不支持相应消息块时再使用纯文本。
答案超过单条限制
按段发送，并在每段维护代码围栏状态，保证下一段不会继承错误的 Markdown 语境。
发送完成
运行记录保存频道、线程和消息位置，为查询、反馈和恢复发送提供关联。

稳定请求编号和确定生成的客户端消息编号让重试尽量收敛到同一条回复。Slack API 和 PostgreSQL 之间没有共同事务，发送超时且结果不确定时保留未知状态，恢复前先查询已有投递。

Web 登录怎样确认团队和用户

Web 使用 Slack OpenID Connect 认证浏览器用户。发起登录时建立一次性状态、随机数和 PKCE 校验值，并用受保护的短期 cookie 绑定这次登录。回调交换授权码后，服务验证令牌签名、签发方、受众、有效期、随机数、团队和用户。

登录成功后，浏览器只持有不透明的安全 cookie。数据库保存会话令牌的哈希；原始值只在浏览器和当前请求中出现。允许用户规则在登录和每次已认证请求中都会检查。

检查保护的边界
一次性状态和浏览器事务 cookie回调必须属于当前浏览器发起的登录
PKCE截获授权码的一方不能单独换取令牌
签名、签发方和受众身份令牌来自预期服务并签发给当前应用
随机数和有效期令牌属于当前登录且仍然有效
团队和用户身份落在当前服务允许的工作区和用户范围

Web 对话怎样限制所有权和并发

浏览器创建独立的 Web 对话。每次读取、提交输入、取消和订阅事件都把身份提供方、团队和用户作为查询条件；知道另一个对话的编号无法绕过所有权检查。

修改请求同时验证准确的同源信息和基于登录会话生成的 HMAC 防伪令牌。浏览器 cookie 使用 Secure、HttpOnly 和 SameSite 属性。每段 Web 对话同一时间只允许一个活跃请求，重复点击或网络重试不会从同一份旧历史启动两个执行分支。

会话归属Web 登录会话负责证明浏览器用户，Web 对话负责保存该用户的一段连续交互，执行请求负责一次具体处理。它们在数据库中分别存储，并通过所有者和稳定编号关联。

Web 只发送页面需要的执行事件

内部事件可能包含工具参数、完整结果、权限元数据和追踪信息。Web 投影器把它们转换成浏览器允许接收的状态、脱敏文字、最终消息和必要错误。

每个订阅者使用有界缓冲。页面刷新或网络重连时先取得当前快照，再接收之后的增量，因此不会只显示回复的后半段。浏览器最终把完整消息加入历史，流式缓冲随请求结束清理。

共享分别维护

PostgreSQL 会话事件、Redis 协调和运行投影Slack 收件箱与 Web 浏览器会话

Web 当前使用较窄的工具目录，不注册 Slack 和提醒等入口特有能力；MCP 工具在运行前按用户连接延迟加入。这个差异位于产品与入口组装，不修改共享执行器。
