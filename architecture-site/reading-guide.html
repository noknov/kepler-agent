READING / CONCEPTS

阅读方法与术语

先确认模块职责，再沿请求路径理解状态变化。遇到重试、恢复或授权问题时，核对条件、执行主体、保存的记录和预期结果。本页统一术语，并说明本指南如何组织技术说明。

本章要点

先统一概念，再讨论行为

  • 同一个概念使用同一个名称；代码标识保留原文。
  • 说明行为时，写明条件、主体、动作和结果。
  • 说明恢复时，分别列出已知事实和未知状态。

按目标选择阅读路径

阅读目标建议顺序读完后应能回答
理解系统产品边界 → 执行过程 → 实现索引谁接收请求？谁执行？记录存在哪里？
理解模型与工具上下文与模型 → 工具与策略模型看见什么？工具在什么条件下可以执行？

统一术语

中文名称用于解释概念。英文名称和代码标识用于查找实现。不同层级的标识不能互相替代。

产品配置profile选择存储、模型、工具、凭据和策略的组装层。

按条件、动作和结果阅读

每个机制都应能回答四个问题：什么条件触发？哪个组件负责？组件执行什么动作？系统留下什么证据？

例：工具调用开始后，进程退出

条件会话中存在工具开始记录，但没有对应结果。
主体接管该会话的执行器。
动作执行器按恢复逻辑核对调用，并保留中断或未知状态。
边界外部写入可能已经生效。重试前需查询下游，或使用下游支持的稳定幂等标识。

继续核对恢复机制和工具调用边界。界面显示的完成状态不能单独证明外部操作的结果。

技术说明的写作规则

本指南借鉴 ASD-STE100 的受控词汇、明确主体、短句和单一主题原则。ASD-STE100 是英文技术写作规范；这里将这些原则用于中文说明，不作标准符合性或认证声明。

  1. 一个概念使用一个名称。首次出现时写出中文名称和英文标识。后文使用统一名称，避免在“执行”“请求”“轮次”之间随意替换。
  2. 写明执行主体。使用“执行器保存工具结果”，避免使用“结果会被处理”。主体应能对应到一个模块。
  3. 一句话说明一个主要动作。将顺序动作拆开。先写前置条件，再写动作和结果；复杂流程使用有序步骤。
  4. 把限制写在相关动作旁边。说明重试时，同时说明可重试条件。说明审批时，同时说明审批绑定的调用和参数。
  5. 用记录说明状态。写出用于核对的事件、标识或测试。没有证据时保留“未知”，不要把推测写成完成事实。
含糊表达明确表达
失败后会自动处理。投影写入失败后，投影层从会话事件重建数据。
批准后就可以执行。收到批准后，执行器取回原调用参数，并重新检查能力策略。
请求已经完成。执行器已保存终态。消息投递状态仍需单独核对。

从说明追踪到实现

本网站解释架构。运行步骤、配置和排障命令由项目文档维护。核对行为时，先确认当前代码版本，再查看对应实现和测试。

  • 产品边界：架构指南。
  • 执行机制与失败窗口：架构详解。
  • 验证范围：开发与验证。
