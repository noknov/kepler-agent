系统架构

这套系统接收用户任务，调用模型决定下一步，执行经过检查的工具，再把结果返回用户。Slack、Web 和benchmark adapter 共用执行核心，但使用不同的身份、存储、工作区和投递方式。

模块职责

模型负责生成答复或提出工具调用；真正读取文件、运行命令和访问外部服务的，是应用中的工具。应用还必须决定谁可以执行、到哪里执行、如何保存结果，以及进程退出后如何继续。这些职责不能由一段提示文字代替。

系统将这些职责分成入口适配器、产品配置、执行器、模型与工具适配层，以及会话事件存储。下面的划分描述责任归属，不表示每一层都对应独立部署的服务。

入口适配器与产品配置

入口适配器处理来自具体产品的请求。Slack 需要验签和线程映射；Web 需要浏览器登录与会话归属；benchmark adapter 需要工作区和终端输入。它们将输入整理成核心可以处理的请求。

产品配置（profile）负责选择执行依赖。例如，托管产品使用 PostgreSQL 和服务端工具策略，本地产品使用 JSONL 与本机沙箱。同一个执行器可以通过不同依赖运行，不需要为每种入口复制一套模型循环。

执行器与适配层

执行器负责推进任务：加载记录、构造上下文、请求模型、检查工具调用、保存结果并判断是否结束。它依赖内部约定的请求和结果，不直接处理 Slack 签名或某家模型的网络格式。

模型适配器把内部请求转换为提供方协议。工具实现把检查后的调用转换为文件、命令或外部 API 操作。会话事件存储则保存输入、模型消息、工具生命周期和终态，供后续恢复与查询。

产品边界

“共用执行核心”指产品使用相同的执行机制，不表示工具在同一个地方运行，也不表示它们共享全部登录和会话规则。这个区别直接影响权限、数据位置和故障恢复。

托管 Slack 与 Web

工具在操作员管理的服务端工作区运行。用户发来一个仓库路径，不会自动使该路径成为可访问的服务器目录。服务端配置和用户集成授权共同决定可以访问的资源。会话、入口任务和追加输入由对应的托管存储维护。

Benchmark 接入

工具在用户选择的本地工作区运行，会话写入本机 JSONL。评测进程接收一次输入并输出 JSONL，不维护交互界面。本地工具的文件边界和审批规则不同于托管服务。

说明示例

同一项代码调查，不同执行位置

在 Slack 中要求检查登录代码时，执行者读取的是服务端已配置的仓库。使用benchmark adapter 时，读取的是当前选择的本机工作区。

两次调查都可以使用相同的模型与工具循环，但一个产品成功访问文件，不证明另一个产品也有同样的目录和凭据。

具体入口行为分别见 Slack 和 benchmark adapter。

系统调用关系

以“检查登录失败原因，运行相关测试，并解释结果”为例，用户的一条要求通常需要多次模型判断。模型先决定读取什么，应用执行读取；模型看到代码后再决定运行哪个测试，应用执行命令；模型最后依据实际结果作答。

用户输入 → 入口验证与路由 → 产品配置
                           ↓
                    共享执行器
            构造上下文 → 请求模型
                         ↓
                  答复 或 工具调用
                         ↓
              策略检查 → 工具执行 → 保存结果
                         ↓
                 继续请求模型 或 记录终态
                         ↓
                   入口投递与查询投影

托管入口的持久队列解决“请求已收到，工作进程尚未处理”的交接。会话锁解决“同一历史只能由谁继续推进”。执行事件解决“已经发生了什么”。结果投递解决“用户是否看到了回复”。它们保护的是不同边界。

因此，请求被接受不等于模型已完成；模型已完成也不等于工具修改已被确认；执行完成更不等于消息投递成功。排障时必须分别核对这些事实。

状态与权限约束

这些边界是实际设计约束，不是理想效果的概括。它们决定了系统在正常执行和异常退出时如何处理。

  • 权限由实际执行策略决定。模型看到工具、用户点击确认，都不能增加服务端未授予的宿主机能力。
  • 同一会话的执行需要串行推进，避免两个任务根据同一旧历史作出互不知情的操作。不同会话之间的业务冲突仍要由下游解决。
  • 恢复先看会话事件。运行列表和界面状态用于展示，不能覆盖工具已经保存的结果。
  • 外部操作结果未知时，先查询下游。内部超时不能证明外部操作没有生效。
  • 投递失败只修复投递，不为了补发消息重跑已经完成的模型和工具。

例如，工具请求已经发出，进程却在保存结果前退出。新的执行者不能根据“数据库没有结果”推断工具没运行。它需要保留未知状态，结合外部记录判断。完整恢复过程在持久化章节说明。
