01 / MENTAL MODEL

系统边界

系统把 Slack 中的用户请求转换为一次 Agent turn，并围绕这次 turn 组织会话上下文、模型工具循环、工具权限、生命周期事件和运行记录。

交互与传输层
Slack GatewaySlack WorkerJSON-RPC App ServerCLI
Agent 核心层
Agent CoreRunnerMemory PipelineTool RegistryEvent Protocol
基础设施层
PostgreSQL · 权威状态Redis · 协调与缓存LLM ProvidersExternal Systems

模块边界：agentcore 和 agentprotocol 不包含 Slack、HTTP 或部署拓扑假设。Slack、App Server 和 PostgreSQL 相关代码作为适配层接入核心执行模型。

Durable

PostgreSQL 保存事实

会话、运行、步骤、协议事件、反馈、提醒和大型工具输出都以 PG 为准。

Ephemeral

Redis 负责协调

用于唤醒、缓存、活动运行 owner、跨 Pod 控制和近似并发计数。

Neutral

Core 不绑定 Slack

同一套执行内核可被 Slack worker、stdio app-server 或未来其他入口调用。

02 / RUNTIME TOPOLOGY

系统以哪些进程运行

系统可以用一个 all-in-one 进程运行，也可以拆分为多个服务进程。拆分形态下，入口、执行、观测和通用协议服务分别部署。

进程负责什么主要依赖
gatewaySlack Events / Interactions HTTP 入口；验签并持久化事件PostgreSQL、Redis
worker领取 inbox 事件、执行 Agent、回复 Slack、运行后台任务PG、Redis、LLM、Slack API
observability运行记录、成本指标、工具健康检查和 dashboardPostgreSQL、Redis
app-server通过 stdio JSON-RPC 暴露通用 Agent CorePG、Redis、LLM
slack-copilot-agent把 Slack 和运维职责组合在一个进程中以上全部

进程关系

gateway 负责接入和入队；worker 负责领取事件并执行 Agent；observability 读取运行记录并提供指标视图；app-server 通过 JSON-RPC 暴露 transport-neutral Agent Core。

03 / REQUEST LIFECYCLE

Slack 请求链路

1 · 验证校验签名、时间戳和请求大小
2 · 持久化按 event_id 写入 PG inbox 去重
3 · 领取Worker 原子获取带期限的租约
4 · 执行锁定会话，驱动 Core 与工具
5 · 提交保存 Session/Run 并回复 Slack

入口与入队

Gateway 校验 Slack 请求后，将事件写入 slack_event_inbox 并返回成功。Redis 发布新事件通知；Worker 同时保留 PostgreSQL 轮询路径。

租约、续租与恢复

Worker 领取任务后写入 claim_owner 和 claim_until。执行期间按周期续租；Worker 崩溃后租约自然过期，其他实例可以恢复事件。完成、失败和续租都校验当前 owner，防止旧 Worker 覆盖新 Worker。

投递语义：这是至少一次处理，不是分布式“恰好一次”。如果 Slack 回复成功后、inbox 完成标记前进程崩溃，极小窗口内仍可能出现重复回复。

会话串行化

Conversation Service 使用 PostgreSQL advisory lock 串行化同一个 Slack thread 的 turn。会话加载、模型调用、工具执行和状态保存位于同一会话锁生命周期内。

Steering 与取消

运行中的新消息进入 steering 队列，在下一模型步骤前注入；取消语义会终止当前 context。活动运行的 owner Pod 记录在 Redis，其他实例通过 Pod 控制频道转发 steering 或 cancel。

04 / EXECUTION ENGINE

Core 与 Runner

Core 管理 turn 生命周期、事件发布和执行边界；Runner 管理模型调用、工具调用和最终回答验证。传输层通过 hooks 和 protocol events 观察执行过程。

Agent Core

执行边界

接收 TurnRequest，克隆每次运行的 Registry，绑定 observer/hooks，发布标准生命周期事件。

Agent Runner

多步模型—工具循环

构建上下文、调用模型、标准化工具调用、执行工具、注入结果，直到完成或等待用户输入。

Runner 迭代

  1. 检查取消状态并注入新到达的 steering。
  2. 计算消息、工具 schema 和输出预算，必要时压缩上下文。
  3. 调用流式或非流式 LLM，并标准化不同 Provider 的响应。
  4. 没有工具调用时验证最终回答；有工具调用时执行并追加结果。
  5. 检测重复调用、工具连续失败、缺少信息和最大步骤限制。

最终回答验证

进度 narration 可以实时输出，最终答案在提交前会进行检查。检查项包括原始证据倾倒、缺少代码证据的文件引用、文本化工具标记和重复输出。

恢复策略

空响应会重试；限流和过载遵循 Retry-After 或指数退避；prompt 过长会触发强制压缩；达到输出上限时允许受控续写；达到最大步骤时会执行一次禁止工具调用的证据总结。

05 / MEMORY

上下文构建

Memory Pipeline 将系统规则、会话摘要、压缩边界、Slack 线程上下文、历史 turns、当前用户消息和工具证据组合为模型输入。

层次内容生命周期
长期记忆Session Summary跨多个 Turn 持续存在
短期记忆最近的用户、助手和工具 Turns直到达到压缩阈值
外部证据重新拉取的 Slack thread context当前请求；默认不进入摘要
大型结果PostgreSQL Tool Spill按 offset / limit 按需回读

模型实际看到的顺序

System Prompt → Session Summary → Compact Boundary → External Evidence → Persisted Turns → Current User

压缩与大型结果

上下文接近预算时，系统会清理旧工具结果、压缩大型输出或生成会话摘要。超大的工具结果写入 PG spill，模型上下文中保留预览和按需读取方式。

06 / TOOLS & CAPABILITIES

工具与能力

每个工具声明名称、JSON Schema、风险、依赖、surface 和并发属性。Registry 控制模型当前可见的工具集合，Capability Policy 控制服务器实际可执行的工具集合。

Read

读取与诊断

代码搜索、文件读取、Git、Web、Runbook 和基础设施查询。

Write

本机写操作

默认关闭，仅精确名称进入 operator allowlist 后可用。

External write

外部副作用

发送、修改或触发外部系统，同样需要服务端明确授权。

延迟工具发现

GitHub、浏览器、Kubernetes、GCP、代码图谱等工具按类别延迟注册。模型可通过 tool_search 查询并激活当前 turn 需要的工具 schema。

并发规则

声明为 parallel 的只读工具可以并发执行；写工具和非并行工具形成串行屏障。每个 Turn 克隆 Registry，因此一个运行激活的 deferred tools 不会泄漏到另一个运行。

07 / EVENT PROTOCOL

事件协议

协议版本 1.0 用 thread、turn 和 item 描述 Agent 执行过程。Slack、stdio app-server 和其他传输层可以使用同一组生命周期事件表达进度、工具调用、完成、失败和取消。

thread.started传输线程建立
turn.started一次 Agent 请求开始
item.*消息、工具、增量和错误
turn.*完成、失败或取消
thread.closed传输生命周期关闭

内存 Broker 提供进程内订阅、每线程序号和有界历史。生产服务可将协议事件追加到 agent_protocol_events，消费者可按 sequence replay。

配置事件存储后，stdio App Server 声明 eventReplay=true，并提供 events/replay JSON-RPC 方法。

08 / DATA & CONCURRENCY

数据与并发

存储职责故障后的行为
PostgreSQLSession、Run、Step、Feedback、Spill、Inbox、Protocol Events、Reminder、User Preferences不可用时拒绝需要持久状态的工作
Redis唤醒、缓存、去重、活动 owner、跨 Pod 控制、全局计数部分路径 fail-open 或退化为 PG 轮询

运行记录

agent_runs 保存聚合摘要；持续增长的模型步骤和工具步骤写入 append-only agent_run_steps；反馈写入 agent_run_feedback；协议生命周期事件写入 agent_protocol_events。这样避免每一步重写大型 JSONB，也防止并发 observer 用旧快照覆盖新状态。

Schema 管理

DDL 是创建或改变数据库结构的 SQL，例如 CREATE TABLE 和 ALTER TABLE。运行时代码不执行 DDL，只做只读的完整性检查。当前目标结构集中在 schema/postgres.sql，数据库升级由 operator 或部署仓库中的轻量 migration 流程负责。

并发控制

进程内 semaphore 限制单 Worker 并发；Redis 计数器近似限制集群并发；PG advisory lock 串行化同一 Session。它们分别解决资源上限、跨 Pod 总量和会话一致性。

09 / SAFETY BOUNDARY

安全边界

工具执行权限由服务端 Capability Policy 控制。新写工具默认禁用，只有精确工具名加入 operator allowlist 后才会暴露或执行。

Identity

入口身份

Slack HMAC 和时间戳验证；允许用户和频道列表限制谁可以发起任务。

Filesystem

工作区边界

真实路径和符号链接必须落在配置根目录；敏感密钥、云凭据和环境文件默认拒绝。

Commands

argv 执行

命令不通过 shell 拼接，策略检查程序、参数、工作目录和危险模式。

Boundary

Sandbox 边界

当前主要是应用层策略约束，不等同于进程、容器或内核级隔离。

每次工具调用前会生成 tool_policy_decision 事件，记录工具名、风险、surface、允许/拒绝和原因。

公共 HTTP 客户端拒绝 localhost、私网和特殊地址，并在 DNS 解析后复查，降低 SSRF 与 DNS rebinding 风险。Redactor 会从日志和错误中清理 token、Authorization header、私钥和工作区绝对路径。

可用性与观测

03 / REQUEST LIFECYCLE

Slack request flow

1 · VerifySignature, timestamp, and size
2 · PersistDeduplicate by event_id in PG
3 · ClaimWorker obtains a timed lease
4 · ExecuteLock session, run Core and tools
5 · CommitSave state and reply to Slack

Ingress and enqueueing

Gateway verifies the Slack request, inserts the event into slack_event_inbox, and acknowledges Slack. Redis publishes a wakeup notification; workers also retain a PostgreSQL polling path.

Leases and recovery

A claim records claim_owner and claim_until. The worker renews the lease while executing. After a crash, the lease expires and another worker recovers the event. Completion, failure, and renewal are owner-checked.

Delivery semantics: processing is at-least-once, not distributed exactly-once. A crash after an external Slack write but before inbox completion leaves a narrow duplicate-reply window.

Session serialization

The Conversation Service serializes turns for the same Slack thread with a PostgreSQL advisory lock. Session load, model calls, tool execution, and state save happen within that lock lifetime.

Steering and cancellation

New messages join a steering queue and are injected before the next model step. Active-run ownership lives in Redis, allowing another pod to forward steering or cancellation to the owner.

04 / EXECUTION ENGINE

Core and Runner

Core manages turn lifecycle, event publishing, and execution boundaries. Runner manages model calls, tool calls, and final-answer validation. Transports observe execution through hooks and protocol events.

Agent Core

Execution boundary

Accepts TurnRequest, clones a per-run Registry, binds observers and hooks, and publishes lifecycle events.

Agent Runner

The model–tool loop

Builds context, calls the model, normalizes tool calls, executes tools, appends evidence, and repeats.

Runner iteration

  1. Check cancellation and inject queued steering.
  2. Budget messages, tool schemas, and output; compact when necessary.
  3. Call a streaming or non-streaming provider through normalized interfaces.
  4. Validate a final answer or execute and append requested tools.
  5. Detect repetition, repeated failures, missing information, and step limits.

Final-answer validation

Progress narration may stream during execution. The final answer is checked before commit for raw evidence dumps, unevidenced code references, textual tool markup, and repetitive output.

Recovery policy

Empty responses retry; overload and rate limits use Retry-After or backoff; oversized prompts force compaction; truncated output can continue; the final step becomes a tool-free evidence summary when the limit is reached.

05 / MEMORY

Context construction

The Memory Pipeline combines system rules, session summary, compact boundaries, Slack thread context, historical turns, current user input, and tool evidence into model input.

Model-visible order

System Prompt → Session Summary → Compact Boundary → External Evidence → Persisted Turns → Current User

Compaction and large results

When context approaches the budget, the system clears old tool results, compresses large outputs, or generates a session summary. Very large tool output moves to PG spill with a preview and instructions for reading more.

06 / TOOLS & CAPABILITIES

Tools and capabilities

Every tool declares a name, JSON Schema, risk, dependencies, surfaces, and concurrency behavior. The Registry controls the model-visible tool set; Capability Policy controls the server-executable tool set.

Read

Read and diagnose

Code search, file reads, Git, web, runbooks, and infrastructure queries.

Write

Host mutation

Disabled by default and enabled only by exact operator allowlist name.

External write

External side effects

Send, modify, or trigger remote systems with explicit server authorization.

Deferred discovery

GitHub, browser, Kubernetes, GCP, code graph, and similar tools are registered by category. The model can use tool_search to discover and activate the schemas needed for the current turn.

Concurrency rules

Parallel-safe read tools may run concurrently. Writes and non-parallel tools create a serial barrier. Each turn clones its Registry, so deferred activation never leaks across runs.

07 / EVENT PROTOCOL

Event protocol

Protocol 1.0 describes agent execution as threads, turns, and items. Slack, stdio app-server, and other transports can use the same lifecycle events for progress, tool calls, completion, failure, and cancellation.

thread.startedTransport thread begins
turn.startedAgent request begins
item.*Messages, tools, deltas, errors
turn.*Complete, fail, or cancel
thread.closedTransport lifecycle ends

The in-memory Broker provides in-process subscription, per-thread sequence numbers, and bounded history. Production services can append protocol events to agent_protocol_events; consumers replay by sequence.

When an event store is configured, the stdio App Server advertises eventReplay=true and exposes the events/replay JSON-RPC method.

08 / DATA & CONCURRENCY

Data and concurrency

StoreResponsibilityFailure behavior
PostgreSQLSessions, runs, steps, feedback, spills, inbox, protocol events, reminders, preferencesDurable operations reject work when unavailable
RedisWakeups, caches, deduplication, active owner, pod control, global countersSelected paths fail open or fall back to PG polling

Run records

agent_runs stores the aggregate summary. Growing model/tool steps go to append-only agent_run_steps, feedback goes to agent_run_feedback, and lifecycle protocol events go to agent_protocol_events.

Schema management

Runtime code executes no DDL; it only verifies required tables. schema/postgres.sql is the current contract, while operators or the deploy repository's lightweight migration flow own upgrades.

Concurrency control

A local semaphore limits each process, a Redis counter approximates the cluster total, and a PG advisory lock serializes a session.

09 / SAFETY BOUNDARY

Safety boundary

Tool execution is governed by server-side Capability Policy. New write tools start disabled and become available only when an operator allowlists the exact tool name.

Identity

Ingress identity

Slack HMAC and timestamps verify requests; user and channel allowlists restrict initiation.

Filesystem

Workspace boundary

Resolved paths and symlinks must remain under configured roots; credentials and secret files are denied.

Commands

argv execution

No shell string assembly; policy checks programs, arguments, working directories, and dangerous patterns.

Boundary

Sandbox boundary

The current controls are application-level policies, not process, container, or kernel isolation.

Before each tool call, the runner emits a tool_policy_decision event with the tool name, risk, surface, allow/deny result, and reason.

Public HTTP clients reject localhost, private, and special-use addresses and re-check resolved IPs. Redaction removes tokens, Authorization headers, private keys, and absolute workspace prefixes from logs and errors.

10 / RELIABILITY & OBSERVABILITY

Reliability and observability

Lifecycle

Drain and shutdown

Stop claiming new work, wait for active events, then close HTTP and background tasks within deadlines.

Recovery

Retry and dead letter

Backoff, jitter, bounded attempts, and expired-lease recovery protect the inbox.

Evidence

Durable run traces

Steps, usage, cost, errors, quality signals, feedback, and trace/span identifiers are persisted.

Operational surfaces include /livez, /readyz, loopback-only /drain, run lists, metrics, and tool health. Run trace records model steps, tool calls, errors, usage, cost, and final state.

Run quality now aggregates automatic signals such as termination reason, tool errors, policy denials, retries, recovery, truncated output, and user feedback. The Slack inbox also reports queue depth, lease loss, dead letters, queue full events, and completion counts.

Tracing currently uses custom identifiers and PostgreSQL records rather than an OTLP exporter. /metrics is product-oriented JSON, not a full Prometheus surface.

Open areas

Still evolving

  • External-write idempotency / outbox
  • Stronger sandbox boundary
  • Split configuration domains
  • Standard OpenTelemetry export
  • Multi-agent run trees

Capacity boundaries

PG advisory locks occupy a connection for the full agent turn; Redis concurrency counters have TTLs and fail open; reminder claims use a one-minute lease without renewal.
