架构

Kepler Agent

Kepler Agent 接收 Slack、网页和本地终端中的用户请求，让模型在明确的工具与权限范围内完成工作。三个入口共用同一套请求执行逻辑；入口负责身份、通信和显示，产品配置负责选择存储、工具和权限，执行器负责模型与工具之间的循环。

系统由五部分组成

下面五部分足以解释绝大多数代码的归属。一次请求从入口进入，经过产品组装后交给共享执行器；执行器调用模型和工具，并把事实写入记录；入口根据执行事件更新 Slack、网页或终端界面。

部分负责的事情主要目录
入口Slack 验签和消息线程、网页登录和对话所有权、终端输入与渲染、应用协议packages/surfaces、packages/appserver、apps/cli
产品组装把运行场景需要的模型客户端、工具目录、权限规则、提示内容和存储实现交给执行器packages/profiles/hosted、packages/profiles/local

一条请求经过哪些阶段

这条主线是阅读其他页面和源码时的坐标。Slack、Web 和命令行的接收方式不同，但进入产品配置之后都执行相同的步骤。

  1. 入口确认请求可以接收。Slack 校验原始请求体、时间和签名；Web 校验登录、对话所有权、来源和防伪令牌；本地终端取得当前用户和工作目录。
  2. 产品层补齐运行依赖。它选择本次请求使用的模型、提示内容、工具集合、权限规则、事件存储、附件存储和执行中的输入来源。
  3. 执行器取得这段对话的处理权。进程内锁保证单个进程里的顺序；托管环境再使用数据库处理权，避免多个工作进程从同一份历史同时继续。
  4. 读取记录并处理上次中断留下的状态。已经结束的相同请求直接恢复结果。只有开始记录而没有结果的模型请求或工具动作会先补成明确的中断事实。
  5. 组成模型本次能够看到的内容。系统说明、已有消息、摘要、工具结果和当前工具定义共同组成请求。旧内容按完整交互分组裁剪，不拆开工具请求与结果。
  6. 模型给出文字或要求使用工具。模型接入层处理服务协议、流式事件、有限重试和备用服务；执行器只处理统一后的消息和工具请求。
  7. 工具经过检查后执行。系统核对工具是否公开、参数是否有效、权限是否允许以及是否需要批准。独立读取可以并行，修改操作保持顺序。
  8. 工具结果回到上下文，模型继续判断。这个过程可以重复。执行期间到达的新消息会在稳定边界加入，不会插进一批工具的执行中间。
  9. 完整结果落入记录，入口完成呈现。最终消息和结束原因先形成可恢复事实。Slack、Web 和终端根据相同事件更新各自的显示。

贯穿实现的四条规则

这些规则决定了代码为什么按现在的方式分层，也能帮助判断一个改动应该落在哪个包。

模型与工具的循环只有一份实现

代码约束Slack、Web、命令行和应用服务不各自实现模型循环。
实际结果上下文裁剪、工具并发、压缩、恢复和结束条件在各入口保持一致。
扩展方式新入口负责转换输入和输出，再通过产品配置使用共享执行器。

会话事件记录已经确认发生的事实

写入内容用户输入、完整模型消息、工具开始与结果、批准、压缩和请求结束。
使用位置上下文、崩溃恢复、执行轨迹和运行查询视图都从这些事件生成。
界面关系文字片段和动态状态用于及时显示；恢复时读取完整事件，不读取半条界面文本。

托管环境和本地环境使用不同的安全边界

托管环境服务端工具策略直接决定允许范围。修改型工具需要由运维配置精确开放，用户界面上的表述不能授予服务器权限。
本地环境工作区路径、命令参数、网络、操作系统沙箱和用户批准共同限制动作。
共享部分工具仍使用相同描述、调用和结果协议，差异通过产品配置注入。

可重建数据不参与恢复决策

权威数据按顺序写入的会话事件，以及入口队列和追加输入队列各自的持久状态。
查询数据运行列表、步骤、费用、状态提示和健康汇总可以从权威事实重新生成。
拥堵处理派生通知可以合并或触发重建；权威记录写入失败时请求不能假装已经保存。

三个入口怎样使用共享系统

入口请求从哪里来运行位置与存储入口特有职责
Slack经过验签的事件和同一消息线程里的后续回复服务端工作区；会话事件保存在 PostgreSQL可靠收件箱、消息与附件整理、原生流式回复、线程状态和工作流选择
Web已经登录的浏览器对话服务端工作区；Web 对话按所有者单独保存OIDC 登录、浏览器会话、同源与防伪检查、SSE 事件和展示字段过滤
本地命令行终端输入、标准输入或命令参数用户机器；每段对话保存为本地 JSONL工作区限制、操作系统沙箱、交互批准、终端渲染和无界面输出

Slack 按频道与消息线程查找历史，Web 按登录用户和 Web 对话查找历史，本地命令行读取用户机器上的记录。三者找到历史后都交给同一个执行器处理。
