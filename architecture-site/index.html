01 / MENTAL MODEL

先建立一个正确的心智模型

它不是一个“接上 LLM 的 Slack Bot”，而是一套由交互适配器、Agent 执行内核、云端运行基础设施组成的服务框架。

交互与传输层
Slack GatewaySlack WorkerJSON-RPC App ServerCLI
Agent 核心层
Agent CoreRunnerMemory PipelineTool RegistryEvent Protocol
基础设施层
PostgreSQL · 权威状态Redis · 协调与缓存LLM ProvidersExternal Systems

边界原则：agentcore 和 agentprotocol 不知道 Slack、HTTP 或部署拓扑；Slack、App Server 和 PostgreSQL 都是适配器。

Durable

PostgreSQL 是事实来源

会话、运行、事件、反馈、提醒和大型工具输出都只持久化到 PG。

Ephemeral

Redis 是协调加速层

负责唤醒、缓存、跨 Pod 控制和近似的集群并发限制。

Neutral

Core 与渠道无关

同一套模型和工具循环可服务 Slack、stdio 或未来其他 UI。

02 / RUNTIME TOPOLOGY

系统以哪些进程运行

生产形态可以拆分扩缩容，本地也可以合并成一个进程。功能仓库不绑定 Docker、Kubernetes 或 systemd。

进程负责什么主要依赖
gatewaySlack Events / Interactions HTTP 入口；验签并持久化事件PostgreSQL、Redis
worker领取 inbox 事件、执行 Agent、回复 Slack、运行后台任务PG、Redis、LLM、Slack API
observability运行记录、成本指标、工具健康检查和 dashboardPostgreSQL、Redis
app-server通过 stdio JSON-RPC 暴露通用 Agent CorePG、Redis、LLM
slack-copilot-agent把 Slack 和运维职责组合在一个进程中以上全部

为什么要拆开 Gateway 和 Worker

Gateway 的目标是快速、可靠地接收请求；Worker 的执行时间可能从几秒到几分钟。将二者分开，HTTP 接入容量不会被模型延迟或工具执行拖住，Worker 也可以独立按任务压力扩容。

03 / REQUEST LIFECYCLE

一条 Slack 消息如何走完全程

1 · 验证校验签名、时间戳和请求大小
2 · 持久化按 event_id 写入 PG inbox 去重
3 · 领取Worker 原子获取带期限的租约
4 · 执行锁定会话，驱动 Core 与工具
5 · 提交保存 Session/Run 并回复 Slack

先持久化，再确认

Gateway 只有在事件成功写入 slack_event_inbox 后才向 Slack 返回成功。Redis 只发布“有新事件”的提示；即使通知丢失，Worker 也会周期性扫描 PostgreSQL。

租约、续租与恢复

Worker 领取任务后写入 claim_owner 和 claim_until。执行期间按周期续租；Worker 崩溃后租约自然过期，其他实例可以恢复事件。完成、失败和续租都校验当前 owner，防止旧 Worker 覆盖新 Worker。

投递语义：这是至少一次处理，不是分布式“恰好一次”。如果 Slack 回复成功后、inbox 完成标记前进程崩溃，极小窗口内仍可能出现重复回复。

同一线程不会并发改写

Conversation Service 使用 PostgreSQL advisory lock 串行化同一个 Slack thread。加载会话、模型调用、工具执行和保存结果都位于锁的生命周期内，跨 Pod 也不会基于同一份旧状态同时生成两个回答。

Steering 与取消

运行中的新消息进入 steering 队列，在下一模型步骤前注入；取消语义会终止当前 context。活动运行的 owner Pod 记录在 Redis，其他实例通过 Pod 控制频道转发 steering 或 cancel。

04 / EXECUTION ENGINE

Core 与 Runner 如何协作

Core 管生命周期，Runner 管推理循环。这个分工让 transport 只负责输入输出，而不复制模型和工具逻辑。

Agent Core

稳定的执行边界

接收 TurnRequest，克隆每次运行的 Registry，绑定 observer/hooks，发布标准生命周期事件。

Agent Runner

多步模型—工具循环

构建上下文、调用模型、标准化工具调用、执行工具、注入结果，直到完成或等待用户输入。

Runner 的一次迭代

  1. 检查取消状态并注入新到达的 steering。
  2. 计算消息、工具 schema 和输出预算，必要时压缩上下文。
  3. 调用流式或非流式 LLM，并标准化不同 Provider 的响应。
  4. 没有工具调用时验证最终回答；有工具调用时执行并追加结果。
  5. 检测重复调用、工具连续失败、缺少信息和最大步骤限制。

流式回答不是直接透传

过程性 narration 可以实时展示，但候选最终答案会先缓冲并验证。系统会识别原始证据倾倒、虚构代码引用、文本化工具标记和高度重复输出；不合格答案会先修复或重试，不让用户看到已被判定无效的版本。

恢复策略

空响应会重试；限流和过载遵循 Retry-After 或指数退避；prompt 过长会触发强制压缩；达到输出上限时允许受控续写；达到最大步骤时会执行一次禁止工具调用的证据总结。

05 / MEMORY

上下文不是简单堆积

Memory Pipeline 将持久会话、动态 Slack 上下文和当前请求组合成模型输入，并控制它们何时压缩、何时丢弃。

层次内容生命周期
长期记忆Session Summary跨多个 Turn 持续存在
短期记忆最近的用户、助手和工具 Turns直到达到压缩阈值
外部证据重新拉取的 Slack thread context当前请求；默认不进入摘要
大型结果PostgreSQL Tool Spill按 offset / limit 按需回读

模型实际看到的顺序

System Prompt → Session Summary → Compact Boundary → External Evidence → Persisted Turns → Current User

渐进压缩

系统先清理较旧工具结果，再压缩单项大输出，最后才调用摘要模型收拢历史对话。摘要连续失败会熔断，避免每次请求重复消耗。超过约 15K 字符的工具结果写入 PG spill，模型只保留前缀和继续读取的方法。

06 / TOOLS & CAPABILITIES

工具是结构化能力，不是提示词技巧

每个工具都声明名称、JSON Schema、风险、依赖、可用 surface 和并发属性。Registry 决定模型能看见什么，Capability Policy 决定服务器真正允许执行什么。

Read

读取与诊断

代码搜索、文件读取、Git、Web、Runbook 和基础设施查询。

Write

本机写操作

默认关闭，仅精确名称进入 operator allowlist 后可用。

External write

外部副作用

发送、修改或触发外部系统，同样需要服务端明确授权。

延迟发现

重型工具按 code、browser、integration、infrastructure 等类别延迟注册。模型先用 tool_search 找到合适能力，再将 schema 激活到当前运行，降低 token 消耗和误选概率。

并发规则

声明为 parallel 的只读工具可以并发执行；写工具和非并行工具形成串行屏障。每个 Turn 克隆 Registry，因此一个运行激活的 deferred tools 不会泄漏到另一个运行。

07 / EVENT PROTOCOL

完整、版本化的生命周期语言

协议版本为 1.0，用 thread、turn 和 item 描述一次执行，而不是用 Slack message 描述。相同 major 下允许增加字段和未知事件类型；major 变化可以是不兼容升级。

thread.started传输线程建立
turn.started一次 Agent 请求开始
item.*消息、工具、增量和错误
turn.*完成、失败或取消
thread.closed传输生命周期关闭

内存 Broker 支持每线程序号、最近 512 条有界历史和 cursor replay。慢订阅者不会阻塞 Agent；它们断开后按 cursor 重连。不过 stdio App Server 当前声明 eventReplay=false，协议能力尚未完全接入 transport。

08 / DATA & CONCURRENCY

PostgreSQL 管状态，Redis 管协作

存储职责故障后的行为
PostgreSQLSession、Run、Step、Feedback、Spill、Inbox、Reminder、User Preferences不可用时拒绝需要持久状态的工作
Redis唤醒、缓存、去重、活动 owner、跨 Pod 控制、全局计数部分路径 fail-open 或退化为 PG 轮询

运行记录为什么拆表

agent_runs 保存聚合摘要；持续增长的模型步骤和工具步骤写入 append-only agent_run_steps；反馈写入 agent_run_feedback。这样避免每一步重写大型 JSONB，也防止并发 observer 用旧快照覆盖新状态。

DDL 与 Schema

DDL 是创建或改变数据库结构的 SQL，例如 CREATE TABLE 和 ALTER TABLE。运行时代码不执行 DDL，只做只读的完整性检查。当前目标结构集中在 schema/postgres.sql，数据库升级由 operator 或外部部署流程负责。

并发的三层约束

进程内 semaphore 限制单 Worker 并发；Redis 计数器近似限制集群并发；PG advisory lock 串行化同一 Session。它们分别解决资源上限、跨 Pod 总量和会话一致性。

09 / SAFETY BOUNDARY

权限由服务器决定

终端用户确认不能保护云端宿主机，因此写能力不依赖二次确认。服务器的 Capability Policy 是唯一授权来源：新写工具默认禁用，必须由 operator 将精确工具名加入 allowlist。

Identity

入口身份

Slack HMAC 和时间戳验证；允许用户和频道列表限制谁可以发起任务。

Filesystem

工作区边界

真实路径和符号链接必须落在配置根目录；敏感密钥、云凭据和环境文件默认拒绝。

Commands

argv 执行

命令不通过 shell 拼接，策略检查程序、参数、工作目录和危险模式。

Known boundary

当前没有 Sandbox

这是应用层约束，不等同于进程、容器或内核级隔离；不应运行任意不可信代码。

公共 HTTP 客户端拒绝 localhost、私网和特殊地址，并在 DNS 解析后复查，降低 SSRF 与 DNS rebinding 风险。Redactor 会从日志和错误中清理 token、Authorization header、私钥和工作区绝对路径。

10 / RELIABILITY & OBSERVABILITY

服务如何保持可用和可诊断

Lifecycle

Drain 与优雅退出

停止领取新任务，等待活跃事件，在超时内关闭 HTTP 和后台任务。

Recovery

重试与 Dead Letter

事件使用退避、抖动和最大尝试次数；租约过期任务可自动恢复。

Evidence

持久 Run Trace

记录步骤、usage、成本、错误、质量、反馈以及 trace/span 标识。

运维入口包括 /livez、/readyz、本机限定的 /drain、运行列表、指标和工具健康页面。Observability API 默认需要管理 token；无认证模式也只允许明确启用后的 loopback 请求。

当前 trace 主要是自定义 ID 和 PostgreSQL 记录，还没有标准 OTLP exporter；/metrics 也更接近产品指标 JSON，而不是完整 Prometheus 指标面。

01 / MENTAL MODEL

Start with the right mental model

This is not merely a Slack bot connected to an LLM. It is a service framework with interaction adapters, an agent execution core, and cloud runtime infrastructure.

02 / RUNTIME TOPOLOGY

Runtime processes

Production responsibilities can scale independently, while local environments may combine them in one binary. The functional repository does not prescribe Docker, Kubernetes, or systemd.

ProcessResponsibilityMain dependencies
gatewaySlack Events / Interactions ingress; verifies and persists eventsPostgreSQL, Redis
workerClaims inbox events, executes agents, replies to Slack, runs background jobsPG, Redis, LLM, Slack API
observabilityRun history, cost metrics, tool health, and dashboardPostgreSQL, Redis
app-serverExposes the generic Agent Core over stdio JSON-RPCPG, Redis, LLM
slack-copilot-agentCombines Slack and operational responsibilities in one processAll of the above

Why separate Gateway and Worker?

The Gateway must acknowledge requests quickly and reliably; a Worker task may run for minutes. Separation prevents model latency from consuming ingress capacity and lets workers scale with execution demand.

03 / REQUEST LIFECYCLE

The life of a Slack message

1 · VerifySignature, timestamp, and size
2 · PersistDeduplicate by event_id in PG
3 · ClaimWorker obtains a timed lease
4 · ExecuteLock session, run Core and tools
5 · CommitSave state and reply to Slack

Persist before acknowledge

The Gateway acknowledges Slack only after inserting the event into slack_event_inbox. Redis publishes a wakeup hint; workers still poll PostgreSQL when a notification is lost.

Leases and recovery

A claim records claim_owner and claim_until. The worker renews the lease while executing. After a crash, the lease expires and another worker recovers the event. Completion, failure, and renewal are owner-checked.

Delivery semantics: processing is at-least-once, not distributed exactly-once. A crash after an external Slack write but before inbox completion leaves a narrow duplicate-reply window.

One writer per thread

A PostgreSQL advisory lock serializes the complete turn for one Slack thread across pods. Loading the session, model calls, tools, and saving state share that lock lifetime.

Steering and cancellation

New messages join a steering queue and are injected before the next model step. Active-run ownership lives in Redis, allowing another pod to forward steering or cancellation to the owner.

04 / EXECUTION ENGINE

How Core and Runner cooperate

Core owns lifecycle; Runner owns reasoning. Transports remain responsible only for input, presentation, and delivery.

Agent Core

A stable execution boundary

Accepts TurnRequest, clones a per-run Registry, binds observers and hooks, and publishes lifecycle events.

Agent Runner

The model–tool loop

Builds context, calls the model, normalizes tool calls, executes tools, appends evidence, and repeats.

One Runner iteration

  1. Check cancellation and inject queued steering.
  2. Budget messages, tool schemas, and output; compact when necessary.
  3. Call a streaming or non-streaming provider through normalized interfaces.
  4. Validate a final answer or execute and append requested tools.
  5. Detect repetition, repeated failures, missing information, and step limits.

Streaming is not raw passthrough

Progress narration may stream, but a candidate final answer is buffered for validation. Raw evidence dumps, invented code references, textual tool markup, and repetition can trigger repair before the user sees the answer.

Recovery policy

Empty responses retry; overload and rate limits use Retry-After or backoff; oversized prompts force compaction; truncated output can continue; the final step becomes a tool-free evidence summary when the limit is reached.

05 / MEMORY

Context is curated, not accumulated

The Memory Pipeline combines durable conversation state, dynamic Slack context, and the current request while deciding what to preserve, summarize, or discard.

LayerContentLifetime
Long-termSession SummaryAcross many turns
Short-termRecent user, assistant, and tool turnsUntil compaction
External evidenceFresh Slack thread contextCurrent request; excluded from summary by default
Large resultsPostgreSQL Tool SpillRead back by offset and limit

Model-visible order

System Prompt → Session Summary → Compact Boundary → External Evidence → Persisted Turns → Current User

Progressive compaction

Old tool results are cleared first, individual large outputs are compressed next, and an LLM summary is the final step. Repeated summary failures trip a circuit breaker. Tool output above roughly 15K characters moves to PG spill with a small preview and retrieval instructions.

06 / TOOLS & CAPABILITIES

Tools are typed capabilities

Every tool declares a name, JSON Schema, risk, dependencies, surfaces, and concurrency behavior. The Registry controls model visibility; Capability Policy controls actual server authorization.

Read

Read and diagnose

Code search, file reads, Git, web, runbooks, and infrastructure queries.

Write

Host mutation

Disabled by default and enabled only by exact operator allowlist name.

External write

External side effects

Send, modify, or trigger remote systems with explicit server authorization.

Deferred discovery

Heavy tool families are hidden behind tool_search. Schemas are activated only for the current run, reducing token cost and tool-selection noise.

Concurrency rules

Parallel-safe read tools may run concurrently. Writes and non-parallel tools create a serial barrier. Each turn clones its Registry, so deferred activation never leaks across runs.

07 / EVENT PROTOCOL

A complete, versioned lifecycle language

Protocol 1.0 describes execution in threads, turns, and items rather than Slack messages. A known major version may gain fields or event types; a major version change may be incompatible.

thread.startedTransport thread begins
turn.startedAgent request begins
item.*Messages, tools, deltas, errors
turn.*Complete, fail, or cancel
thread.closedTransport lifecycle ends

The in-memory Broker provides per-thread sequences, a bounded 512-event history, and cursor replay. Slow consumers never block execution. The stdio App Server still advertises eventReplay=false, so the transport has not adopted the full Broker capability yet.

08 / DATA & CONCURRENCY

PostgreSQL owns state; Redis coordinates

StoreResponsibilityFailure behavior
PostgreSQLSessions, runs, steps, feedback, spills, inbox, reminders, preferencesDurable operations reject work when unavailable
RedisWakeups, caches, deduplication, active owner, pod control, global countersSelected paths fail open or fall back to PG polling

Why run data is split

agent_runs stores the aggregate summary. Growing model/tool steps go to append-only agent_run_steps, while feedback goes to agent_run_feedback. This avoids repeated large JSONB rewrites and stale observer overwrites.

DDL and schema ownership

DDL means SQL that defines database structure, such as CREATE TABLE and ALTER TABLE. Runtime code executes no DDL; it only verifies required tables. schema/postgres.sql is the current contract, while operators or external deployment systems own upgrades.

Three concurrency layers

A local semaphore limits each process, a Redis counter approximates the cluster total, and a PG advisory lock serializes a session. These constrain host resources, fleet capacity, and conversation consistency respectively.

09 / SAFETY BOUNDARY

The server is the authority

End-user confirmation cannot protect a cloud host. Write capabilities therefore do not depend on approval prompts. Server-side Capability Policy is authoritative: every new write tool starts disabled until an operator allowlists its exact name.

Identity

Ingress identity

Slack HMAC and timestamps verify requests; user and channel allowlists restrict initiation.

Filesystem

Workspace boundary

Resolved paths and symlinks must remain under configured roots; credentials and secret files are denied.

Commands

argv execution

No shell string assembly; policy checks programs, arguments, working directories, and dangerous patterns.

Known boundary

No sandbox yet

These are application controls, not process, container, or kernel isolation. Arbitrary untrusted code is out of scope.

Public HTTP clients reject localhost, private, and special-use addresses and re-check resolved IPs. Redaction removes tokens, Authorization headers, private keys, and absolute workspace prefixes from logs and errors.

10 / RELIABILITY & OBSERVABILITY

Staying available and diagnosable

Lifecycle

Drain and shutdown

Stop claiming new work, wait for active events, then close HTTP and background tasks within deadlines.

Recovery

Retry and dead letter

Backoff, jitter, bounded attempts, and expired-lease recovery protect the inbox.

Evidence

Durable run traces

Steps, usage, cost, errors, quality, feedback, and trace/span identifiers are persisted.

Operational surfaces include /livez, /readyz, loopback-only /drain, run lists, metrics, and tool health. Observability APIs require an admin token unless loopback-only unauthenticated access is explicitly enabled.

Tracing currently uses custom identifiers and PostgreSQL records rather than an OTLP exporter. /metrics is product-oriented JSON, not a full Prometheus surface.
