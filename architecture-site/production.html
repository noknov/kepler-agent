故障诊断

故障诊断要把现象还原为明确状态：请求是否保存、是否有人处理、模型是否返回、工具是否生效、结果是否提交，以及用户是否收到。定位边界之后，再选择恢复动作。

执行与投递的故障边界

同一个“没有回复”现象，可能对应完全不同的失败。盲目重启或重新提交任务，会改变现场，甚至重复已经成功的外部操作。调查应先沿请求路径取得证据。

  1. 接收：入口事件或会话输入是否已经持久保存？没有保存时，后续查询为空是预期结果。
  2. 调度：是否已被认领，当前所有者和期限是什么，是否受准入限制？
  3. 执行：对应 TurnID 有无模型请求、工具开始、工具结果和终态？
  4. 外部效果：开始后没有结果的工具，能否从下游查询实际完成情况？
  5. 呈现：完整结果已保存时，是否只剩流式、最终消息或重连失败？

说明示例

测试结束但用户没有答案

假设工具结果里已经保存测试输出，模型最终答复与终态也存在，而消息投递报错。应调查投递记录和关联消息，不能为了“再试一次”重跑测试和模型。

如果只有工具开始而没有输出，才需要调查命令进程和恢复状态。两种情形都可能表现为用户没收到结果，但处理动作不同。

期限与处理权

系统没有一个统一超时能代表所有阶段。入口响应期限用于及时确认平台请求；任务租约用于认领接管；会话锁用于串行推进；执行期限限制模型、工具和子任务；关闭宽限期用于收尾。

这些值需要协调，但不能互相替代。例如，入口已经超时不表示模型应立即重跑；租约过期允许新处理者接管，也不证明旧工具没有产生副作用。

期限过短会打断仍在正常推进的工作，过长会延迟接管并增加占用。调整前要看实际任务耗时和清理行为，而不是把所有超时一起放大。

积压与资源等待

积压说明进入速度超过某个处理阶段的完成速度，但不自动指出瓶颈在哪里。先比较队列年龄、活跃执行、会话锁等待、数据库连接池、模型限流和工具耗时的同一时间窗口。

如果大量请求都在提供方限流退避，增加工作进程可能只制造更多重试。如果会话锁等待很长，要检查是否集中在同一会话；不能只增加同一历史的并行执行。

如果模型已经完成而界面迟迟无变化，要分离投影和投递积压。应用仍可能正常保存执行事件，只是呈现消费者变慢。恢复范围应落在实际变慢的阶段。

诊断依据

调查需要能够关联同一次工作的记录。入口 event ID、session ID、TurnID、模型 attempt 和工具 execution ID 属于不同层级。使用错误层级查询，会把有关事件漏掉，也可能把不相关的尝试混在一起。

还需要记录应用版本、配置版本、时间、错误分类和相关脱敏日志。只有“昨天有个请求失败”很难判断是否已经升级、是否配置改变，以及是否同一个外部目标。

每个判断都应区分事实和推断。例如，“保存了 ToolCallStarted”是事实；“外部写入失败了”不是这个事件能够支持的结论。模型报告、摘要和哈希都不能填补缺失的外部完成回执。

Schema 与发布

发布前要核对代码依赖哪个存储契约。新装 schema 用于创建完整结构，增量迁移用于升级已有部署。不能把新装 SQL 当作没有说明的升级步骤；应用运行时也不负责执行 DDL。

迁移需要先有可恢复备份，再按对应版本顺序应用，随后启动匹配代码并验证实际请求。恢复备份和恢复旧镜像是不同操作。

新实例已经接收写入后，旧实例的数据就可能过期。此时简单切回旧机器，可能丢失新写入或重复未知操作。回退需要分别评估数据库、工作区和外部效果，而不能只看哪个镜像曾经启动成功。

验证范围

验证结论必须与实际执行的检查一致。编译证明程序能构建；单元测试证明对应输入和断言成立；集成测试证明配置的测试存储上通过了指定流程。它们不能直接替代真实用户路径。

完整产品验证通常还包含身份认证、一次实际模型响应、必要的工具或集成，以及最终投递。备份能生成文件也不等于可恢复，需要在隔离目标上读取并核对数据。

测试被跳过、没有运行、预期失败和真正通过都应分别记录。失败时先确定是环境配置、应用缺陷还是外部授权问题，再修正对应原因。不要为取得通过状态删掉边界检查。
